# 0042 — the image had never built, and the host that will run it

## The defect

`.dockerignore` excluded `tools/`. The Dockerfile says:

```
COPY tools/connector_check.py tools/session_tail.py ./tools/
```

Docker filters the build **context** before the Dockerfile runs, so those two
files were never sent to the daemon and that `COPY` fails with *file not
found*. **The image has never built.**

Everything downstream pointed at it: 0038's ECS task definition, its one-off
`connector_check` task, the Phase D drill plan, and this commit's own Fly
config. A month of deployment work rested on an artefact nobody could produce.

`tests/test_dockerfile.py` had the right idea aimed at the wrong artefact — it
recomputed the import closure and checked the **COPY list** was complete, and
never asked whether the **context** could deliver it. `fly_stack.context_conflicts`
now reimplements Docker's filter and
`tests/test_fly_runtime.py::test_every_copy_source_survives_the_dockerignore`
runs it on every suite.

### Why the fix is not `tools/*` + `!tools/connector_check.py`

That is the usual idiom, and re-inclusion under an excluded directory is a
corner of Docker's matcher with a [known history of not behaving as
read](https://github.com/docker/cli/issues/2847). There is no Docker daemon in
this sandbox, so the repo cannot exercise it, and **a control whose behaviour
cannot be tested is not a control.**

So `tools/` is simply not excluded any more, and the protection it was there
for — no operator script in the image — is enforced statically instead: the
Dockerfile names every tools file one by one, and a test refuses any `COPY` of
a bare directory. Same guarantee, asserted rather than hoped for.

## Measured, not assumed: the container starts

Reconstructed the image filesystem from the Dockerfile's `COPY` list with the
`.dockerignore` filter applied, and ran it:

- **the import closure is correct** — `main.py` starts, builds the stack, and
  attaches the carry book (`cap $100.00, borrow 0.0000/yr, execution
  overlay/taker, orders: PAPER_TRADING=1: the carry book has no paper venue`);
- **it then exits 1**, fail-closed, because it cannot reach the venue:
  `CRITICAL cannot reach the exchange: time sync transport error`. That is
  correct behaviour and it drives the restart policy below;
- `tools/session_tail.py` runs from inside the tree and prints all four
  invariants, including `promotion gate file is missing; REFUSING` — an image
  with no signed gate cannot go live, which is the right answer.

Bybit is unreachable from this sandbox (the agent proxy returns 403 on the
tunnel), so nothing past the first network call is exercised here. That is what
the drill is for.

## Why Fly, and not the 0038 stack

0038 built 27 CloudFormation resources for a process that makes three decisions
a day and needs one outbound TLS connection. What this book actually needs from
a host is five things:

| need | why | Fly |
|---|---|---|
| one process, never two | two machines is two `CarryEngine`s and two hedges | `strategy = "immediate"`, one region, one volume |
| a disk that survives a deploy | the ledger is the only thing that knows a position exists (D3) | `[[mounts]]` |
| a fixed outbound IP | so the venue key can be pinned to it | `fly ips allocate-egress` |
| secrets at runtime | this image's predecessor shipped live keys in a layer | `fly secrets set` |
| it comes back when it dies | `main.py` exits 1 on an unreachable venue | `restart.policy = "on-failure"` |

`bot/fly.toml` is forty lines. It is generated by `tools/fly_stack.py --render`
and the committed file is parsed and re-checked on every test run, so a hand
edit that weakens a property fails the suite.

## The hazard that is specific to Fly

Fly's job is keeping web apps available and every default points that way.

**`rolling` is the default deploy strategy.** `bluegreen` and `canary` boot a
new machine *alongside* the old one. For an HTTP server that is zero downtime.
Here it is two cold starts and a second $100 short against inventory that backs
one, each with a ledger saying everything is fine. `check()` refuses anything
but `immediate`.

**`auto_stop_machines`** stops a machine nothing is talking to. This process has
no public port on purpose, so that setting would stop a book holding a live
hedge and leave the client unhedged. `check()` refuses `[http_service]` and
`[[services]]` outright — there is nothing to serve, and no reason to be on the
public internet at all.

## What `check()` asserts

Every item is a failure mode, not a style preference:

- `deploy.strategy` is `immediate`; at most one process group; `primary_region`
  set — *two machines is two books*
- no `[http_service]` / `[[services]]`; `restart.policy` brings it back
- exactly one `[[mounts]]` at `/app/state`, and `STATE_DB_PATH` is on it
- no secret-shaped key in `[env]`
- `PAPER_TRADING` is not `0`, `USE_TESTNET` is not `0`, no `LIVE_TRADING_ACK` —
  **a `git push` may not arm live trading**
- `BOOK_MODE=carry` implies `CARRY_BORROW_APR` and `CARRY_EXECUTION_MODE`,
  because `build_bot` raises without them and on Fly that is a crash loop
- the health check's port matches `HEALTHCHECK_PORT`, and its `grace_period` is
  at least the 120s the Dockerfile allows — cold start reconciles against the
  venue *before* the server binds
- `vm.memory >= 512mb` (numpy + scipy + scikit-learn OOM at 256)
- `kill_signal = SIGTERM`

A test also runs `config.load()` on the shipped `[env]`, so the block is
verified against the real parser rather than against a guess about it.

## Deploying it

`python3 tools/fly_stack.py --commands` prints the sequence. Nothing in it
trades: the image ships `PAPER_TRADING=1` and the promotion gate is unsigned,
so the carry broker refuses every order until both change.

Step 7 — `fly secrets set PAPER_TRADING=0` with `USE_TESTNET=1` — is **testnet
only**: `_carry_orders_permitted` returns `(True, "TESTNET")`. Mainnet needs
live authorisation *and* a signed promotion gate on top, and the gate is False.

## What is still not done, and who has to do it

Two of the three things Phase D needs cannot be done from here:

1. **Bybit testnet API keys**, created by a human and IP-pinned to the egress
   IPv4 that step 2 allocates.
2. **Testnet BTC in the wallet.** `CARRY_EXECUTION_MODE=overlay` hedges BTC the
   client already owns; with none, `_open` refuses with `NO_SPOT_INVENTORY` and
   the drill measures nothing.

The third — that the machine can reach the venue at all — is step 5, and it is
read-only.

Until those exist, every venue semantic in INVENTORY §5 stays open: F2 (the
create/query race), F3 (the spot fee charged in BTC), F4 (`positionIM/positionMM`
is not liquidation headroom), F7, F8, and 0040's F10/F11. No amount of further
code closes any of them. **The drill is the only thing that does.**
