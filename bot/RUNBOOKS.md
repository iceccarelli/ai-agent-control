# Runbooks

Short, for a person at a terminal during an incident. Each one says how to **recognise**
it, what state the system is **already in**, what to **do**, and what **never** to do.
Commands that change anything on Fly or on the exchange are the owner's to run; nothing
here is run by the repository.

Standing rules: the carry book is **PAPER / TESTNET only** until the promotion gate is
signed and live is deliberately armed (it is neither). A position, once held, is managed
through every failure below; entries are what stop. The kill switch is cleared by a
human, never by code. Never paste a key, secret, or `.env` into a chat, ticket or log.

Where "read the venue" appears, use the exchange's own web UI or a read-only API key, not
the bot's state, as the authority.

## 1. Venue unavailable (REST or WebSocket down, 403/geoblock, rate-limit ban)
- **Recognise:** `/health` → `healthy:false`, `carry.blocking_fault`, `market_feed.state` not
  RUNNING; logs `VENUE_POSITION_UNREADABLE`, `403`, `IP ban`, `Retry-After`.
- **Already in:** entries refused; a held pair keeps being watched through the venue-position
  read; reads stand down for the cooldown after a 403.
- **Do:** check Bybit status; check the egress IP is the one the API key is allowlisted for
  (`fly ips list --app carry-book`). A **403/geoblock is a refusal, not an obstacle**: do not
  route around it with a proxy, another region or another domain; record the exact response
  and stop.
- **Never:** restart in a loop (each restart re-reads the venue and can extend a ban).

## 2. Unknown order state (a request left, the answer was lost)
- **Recognise:** halt reason `LEG_OUTCOME_UNKNOWN`; order row `reconciliation_required`;
  startup says `unresolved carry order(s)`.
- **Already in:** HALTED, kill switch engaged, nothing sent on top of it. The order id is
  deterministic and is never re-sent under a new id.
- **Do:** read the venue's **order history and open orders** for the symbol, find the
  `orderLinkId` in the log line, and decide: filled / partly filled / not there. If it is
  **not there more than the absence window after the request** (60 s minimum, longer with the
  configured timeouts) recovery proves it never landed on the next start. If it filled, the
  position exists: go to runbook 3.
- **Never:** place a manual "fix-up" order before you know which of those it is.

## 3. Orphan position (venue holds a position the ledger does not)
- **Recognise:** `carry cold start HALTED: the venue holds a perp position … the ledger never
  recorded`, or `VENUE_POSITION_DRIFT`.
- **Already in:** HALTED, kill switch engaged; the ledger is **not** rewritten (the
  disagreement is the evidence).
- **Do:** read the venue position and open orders; decide with the owner whether to close it by
  hand on the exchange (reduce-only). Keep the DB file and the log. Only then clear the kill
  switch (runbook 12) and restart.
- **Never:** edit the ledger to match the venue.

## 4. Orphan or resting order
- **Recognise:** startup refuses on `open orders` the ledger did not expect; the carry
  broker lists a resting order at the venue.
- **Do:** cancel it **on the exchange** (cancels are always allowed) after reading it.
- **Never:** assume a resting reduce-only close is stale: it may be the close in progress.

## 5. Failed protection (a stop is missing or could not be set)
- **Recognise:** `naked_positions` non-empty in `/health`; PROTECT_ONLY on startup.
- **Already in:** unhealthy; PROTECT_ONLY sends nothing except protective actions.
- **Do:** set or verify the stop on the exchange; or close the position by hand (reduce-only).

## 6. Funding mismatch (estimate vs what the venue paid)
- **Recognise:** `funding_unbooked` in `/health`; a supersession entry in the journal.
- **Already in:** estimates are **never cash**; venue-settled rows supersede them by reversal
  (append-only). A row is booked once per `(id, ms, usd, symbol)`.
- **Do:** compare the journal's funding to the exchange's transaction log for the same window.
  A residual after supersession is an incident for a human, not a rounding.

## 7. Wallet mismatch (book vs wallet balances)
- **Recognise:** `ledger.reconcile()` returns `INCIDENT`; the perp-position difference is the
  strict one.
- **Honest limit:** `reconcile()` observes only and is **not run on a timer by the bot**; it is
  run by the report tools. For a client-owned wallet an absolute USDT/BTC comparison is only
  meaningful against a declared slice, which is an owner decision not yet made.
- **Do:** run `python3 tools/carry_report.py`; compare with the exchange; do not adjust the journal.

## 8. Disk full (the Fly volume)
- **Recognise:** `market_feed` store fault `below the … reserve`; SQLite `disk is full` in logs.
- **Already in:** the market-data feed stops writing at its free-space reserve
  (`MARKET_FEED_MIN_FREE_MB`, default 256), **entries stop, a held position is still managed**;
  it resumes by itself with a marked `store_gap`. The ledger is not the feed: if the **ledger**
  cannot write, the book halts with the exposure written down.
- **Measured:** ~1.5 GB per day of feed. A 1 GB volume cannot hold a day. Either extend the
  volume (owner: `fly volumes extend`), set `MARKET_FEED_RETENTION_DAYS`, or leave the feed off.
- **Never:** delete files under the state directory by hand; `trading_state.db*` is the ledger.

## 9. DB corruption (SQLite integrity)
- **Recognise:** `PersistenceError`, `database disk image is malformed`, startup refuses.
- **Do:** stop the machine (owner), copy the volume's files **off the volume first**
  (`fly ssh sftp`), then `sqlite3 copy.db "PRAGMA integrity_check"` **on the copy**. Restore from the
  last verified backup only with the owner's say-so. Recovery never runs on the original.
- **Honest limit:** no automated off-volume encrypted backup exists yet (see "Backups").

## 10. Fly restart / crash loop
- **Recognise:** `fly status` shows restarts; `/health` flaps.
- **Already in:** restart policy `on-failure` ×10; cold start re-reads the venue twice and
  refuses unless both agree; a staged close in flight resumes from its durable log.
- **Do:** `fly logs --app carry-book`; compare `/health` → `fingerprint.code_sha256` and
  `build_commit` with the reviewed commit.
- **Never:** scale to two machines; `fly deploy` without `--strategy immediate --ha=false`.

## 11. Volume loss
- **Recognise:** the machine boots with an empty state directory.
- **Already in:** an empty ledger over a venue that holds a position **HALTs** at cold start
  (it does not open a second hedge).
- **Do:** treat as runbook 3 with no ledger: reconstruct from the exchange's history, with the owner.

## 12. Manual kill switch / clearing it
- **Engage:** the book engages it on every unsafe state. A human can stop the machine
  (`fly machine stop`, owner) — it holds no position of its own; the venue does.
- **Clear (human only):** after you understand why it engaged and the venue is in a state you
  accept, on a copy of the process that owns the DB:
  `StateStore.clear_kill_switch_by_human("HUMAN_CLEARED_KILL_SWITCH")`. The code never calls it.

## 13. API key revoked / leaked
- **Do:** revoke in the Bybit console first, then `fly secrets unset` the old names (owner), issue a
  new key with the **least** permission and an IP allowlist, set it, redeploy. Rotate immediately
  if a secret ever appears in a log, a file or a chat.

## 14. Market recorder down (alert `recorder_down`)
- **Recognise:** Slack/watch alert "the market recorder not recording"; `recorder_state` in the
  last history lines is ABSENT, STALE, UNREADABLE or FAULT (`fly ssh console -a carry-drill -C
  "tail -n 3 /data/monitor/monitor.jsonl"`; the recorder's own file is `/data/market/recorder_status.json`).
- **Already in:** the supervisor restarts the recorder with backoff (`/data/market/supervisor_status.json`
  shows restarts); the monitor and the shadow book are unaffected; entries are not involved (read-only).
- **FAULT with "reserve":** the volume is below the 512 MB reserve. Extend it (owner:
  `fly volumes extend <id> -s <GB>`) or lower `--recorder-retention-days` in the image CMD. The recorder never deletes a day that has no
  verified off-volume copy to free space: `emergency_prunes_denied` in `recorder_status.json` counts the refusals. To let a full volume free its oldest BACKED-UP day,
  run `md_seal.py seal` + `backup` and start the recorder with `--emergency-backup-dir DIR --emergency-receipts R.jsonl` (owner decision).
- **Never:** delete files under `/data/market` by hand; the log is hash-chained and prunes itself by day.

## Backups
`tools/state_backup.py` is the tooling; scheduling and storage are the owner's. It opens the ledger
**read-only**, takes SQLite's online backup (safe beside the writer), checks the copy, and writes a
manifest (SHA-256 and per-table row COUNTS, never contents). It refuses an out-dir on the source's own
directory: a backup beside the ledger on the same volume is not a backup.

    # on the machine, to a scratch dir, then copy OFF the volume (owner):
    python3 tools/state_backup.py backup  --db <PATH-TO-LEDGER> --out-dir <DIR>
    python3 tools/state_backup.py verify  --backup <DIR>/<file>
    # the rehearsal that proves it restores, on a disposable machine/dir (never the live one):
    python3 tools/state_backup.py restore --backup <FILE> --into <NEW-EMPTY-DIR>

The manifest also records each table's newest row id and `PRAGMA user_version`, so `verify` fails a backup whose newest rows or schema version changed even if someone
re-hashed it (a manifest from before this check verifies with a warning, never silently). To INSTALL a restored database after an incident, **with the machine stopped**:

    python3 tools/state_backup.py promote --restored <NEW-EMPTY-DIR>/restored-state.db --live-db <LIVE-PATH> --confirm-owner

It refuses without `--confirm-owner`, if the restored file does not verify against the manifest beside it, if `-wal`/`-shm`/`-journal` exists next to the live file, or if
SQLite cannot take an exclusive lock on it right now. It RENAMES the old file to `<live>.replaced-<UTC>` (never deletes it), installs the copy by atomic rename, and verifies
the result. It does not stop or start anything: stopping the machine first, and checking the result before starting it, are yours.

Encrypt the file before it leaves the machine (`age -r <recipient> -o x.db.age x.db`, or
`openssl enc -aes-256-cbc -pbkdf2 -in x.db -out x.db.enc`) and keep the manifest beside it. A backup that
has not been restored once is a hope, not a backup. **No schedule is installed by the repository.**

## 15. Is the evidence trustworthy, and is it profitable? (read-only, offline)
Run on the recorder's data directory (or a copy; it never writes there):

    python3 tools/profitability_report.py --dir /data/market --history /data/monitor/monitor.jsonl --notional 100000 --hold-days 30

* **Integrity (separate states, no single flag):** every capacity row is validated against `capacity/2`; a row with no chain entry
  is never admitted and blocks the economics block; each file is graded ANCHORED_CURRENT / ANCHORED_LAGGING / STALE_ANCHOR /
  UNANCHORED / ANCHOR_CONFLICT by its LATEST anchor; and the sidecar chain is checked
  against the head copied into `monitor.jsonl` (a second copy on the same volume: external to the evidence directory, not to the machine, until you archive it off the machine). A broken chain in ANY chained file, an anchored file that lost its sidecars or rows, an anchored file that is gone,
  a mixed stream, a regression, a duplicate or more than 1 % rejected rows withholds the economics block entirely; the report says so.
* **Dependence:** unique settlements, not snapshots, are the unit, and settlements are themselves serially dependent:
  a claim needs the effective sample size (>= 30) as well as the count (>= 30 joined, >= 90 for a candidate).
  `INSUFFICIENT` is the honest answer below the floor; a constant funding history has no variance to test and stays INSUFFICIENT.
* **How far to trust the interval (measured, not assumed):** the interval is the widest of a block bootstrap and three
  analytic intervals, and a claim also needs the effective sample size (the LOWER of an autocorrelation estimate and a
  batch-means estimate) to be >= 30. Among series the gate accepts, simulation gives the true mean inside the interval
  about 0.88-0.99 of the time for first-order persistence up to 0.8, and the lower bound above the truth about 3 %.
  Two things it cannot do at ~100 settlements: identify a slow persistent level hidden under noise (measured coverage
  0.7-0.85 there) and predict a level shift. So the economics carry the LEAST favourable of the window's and the most
  recent third's lower bounds, a drift below the window is flagged, and a `RESEARCH_CANDIDATE` is a research flag, never
  a validated edge. `PROSPECTIVE_MARKET_EDGE_SUPPORTED` is the gate a future pre-registration mechanism must satisfy (typed, finite claims,
  screens re-run on post-registration data alone, anchors held off the machine); no registration mechanism exists and this report supplies none,
  so it is unreachable from the CLI today.
* **Money:** two returns (on hedged notional, on fully allocated economic capital), the 10/15/20 %/yr
  screens labelled `PROVISIONAL_SCREENING_HURDLE_NOT_OWNER_APPROVED`, and an explicit list of UNKNOWN
  inputs (latency, the account's real fee tier, venue margin rules). Replace them with the owner's.
* **What a status means:** `PROSPECTIVE_MARKET_EDGE_SUPPORTED` is a statement about the PUBLIC market. `ECONOMICALLY_RECONCILED` needs account
  records (real fee schedule, reconciled account funding settlements, real fills with fee records, measured costs, verified
  margin rules) that nothing in this repository produces yet, so no run of this report can reach it; `EXECUTION_READY` additionally needs a
  separate owner authorisation record. No status authorises trading.
* **What it would take (6b) and what exposure survives (6c):** from the variance and dependence observed so far, the report prints how many
  settlements it would take to separate funding that earns the lowest screen from noise at the family-wise level (an illustrative
  position and an assumed 11.4 bps round trip: labelled ASSUMED). The exposure line is a research ceiling from an offline stress
  simulation (basis shock, funding reversal, gap, liquidity, correlated stackings) with ASSUMED venue rules and an unverified fee tier; it
  is allowed to be, and today is, ZERO, with every reason named. Levels above 1x are analysis only.
* **The other hypotheses (7):** basis convergence is measured as real EPISODES (entry, convergence or failure, adverse widening, net), trend and
  mean reversion are predeclared rules fed one price at a time against buy-and-hold, and all 16 predeclared variants are judged
  together (alpha 0.05/16). They are INSUFFICIENT on a few days of data by design; microstructure cannot be measured until imbalance is recorded and
  a cross-section until more than one symbol is. None is above RESEARCH_CANDIDATE.
* **Never** read it as realised cash: no cash settlement is read from the venue by this tool.

## 18. Does the RUNNING recorder contain this code? (owner, read-only; merging a PR does not change a running machine)
A running Fly machine changes only when an image is built and deployed. Merging PR #217 changes the repository, not
`carry-drill`. To establish what is actually running, from a checkout of the commit you want to compare:

    python3 bot/tools/image_manifest.py expected > expected.txt        # reads only the repository
    python3 bot/tools/image_manifest.py command                         # prints ONE read-only command; run it yourself, save its output as actual.txt
    python3 bot/tools/image_manifest.py compare --expected expected.txt --actual actual.txt
    fly image show -a carry-drill                                       # record the registry image and digest beside the result
    fly status -a carry-drill                                           # machine id, version, restarts

`compare` reports per file MATCH / DIFFERENT / MISSING_ON_MACHINE for the recorder's whole static import closure (computed from the
entry points: recorder, monitor, supervisor and every module they import, including the book, wire, store and transport code) and a verdict. An image built before this change lacks
several of them, which shows as MISSING_ON_MACHINE: that is the expected answer, and it means the old recorder is still
running. The closure includes packages (`signals/`) and LAZY imports: the monitor imports the shadow engine inside a function, so the
trading-engine files that ship in the same image are compared too, and an engine-only edit therefore shows as DIFFERENT even though the
recorder's common path never runs it. Read such a DIFFERENT as "the image is not this commit", not as "the recorder is broken", and
decide the release separately. The drill image carries no commit label, so the tool compares bytes, not tags. **A recorder release is a
separate step from any trading-engine release and needs your explicit authorisation; nothing in this PR requests it.**

## 19. External anchor archive (owner; moves the chain head off the recorder machine)
Chain heads copied into `monitor.jsonl` sit on the same volume as the evidence. To make a rewrite detectable by someone who
controls that volume, keep the heads where the machine cannot reach:

    fly ssh console -a carry-drill -C "tail -n 400 /data/monitor/monitor.jsonl" > monitor_tail.jsonl     # read-only fetch, no secret in it
    python3 bot/tools/anchor_archive.py append --history monitor_tail.jsonl --archive anchors.jsonl        # on YOUR machine
    python3 bot/tools/anchor_archive.py latest --archive anchors.jsonl                                     # prints the archive head

Do this at least daily (the monitor's history is bounded). Store the printed **archive head** (one 64-hex value) and its entry
count somewhere the recorder machine cannot reach: a password-manager note, a mail to yourself, a private repository.
`append` refuses, and writes nothing, if a file's anchor goes BACKWARDS (the evidence was truncated) or the same row count
reappears with a different head (the chain was rewritten). Then, on a copy of `/data/market` on your machine:

    python3 bot/tools/profitability_report.py --dir <copy> --history monitor_tail.jsonl --anchor-archive anchors.jsonl \
        --archive-head <the value you stored> --archive-entries <its count>

The report then says `EXTERNAL_ARCHIVE_HEAD_MATCHES_OWNER_HELD_VALUE` only if the archive is exactly what you recorded (or has
only grown). When it has grown, only the entries inside the prefix you stored count as anchored by the archive (`anchored by the ARCHIVE
itself: N of M chained files` in the report; the grade is ANCHORED only when that equals M): entries appended later are not pinned by you.
The tool cannot see where you keep the value: that remains your claim, and it is printed as one.

The report decides which anchored day-files that are gone were "removed" and which were merely "pruned" from the capacity retention YOU
state (`--capacity-retention-days`, default 365, the recorder's own default; 0 = the recorder keeps everything). It is never read from
the evidence directory, because whoever can delete a day of evidence can also edit a file next to it. If you run the recorder with a
shorter retention, pass the same number here or every legitimately pruned day will block the economics.

A chain sidecar written by an EARLIER revision of this branch (an adoption entry whose hash lacks the mark) does not verify: the entry
is indistinguishable from an ordinary one with the flag flipped onto it, and an anchor cannot tell them apart. Nothing deployed has ever
written one (`evidence_chain.py` first appears in this change), so there is nothing to migrate; a development file would be excluded,
visibly, as SIDECAR_INCONSISTENT.

An automated version of the archive step (a scheduled job that runs the read-only fetch and appends to a private repository) is possible
but needs your decision about where the secrets for it live; it is not part of this PR.

## 20. The prospective evaluation of the BTC funding carry (owner; opens 2026-11-07, closes 2027-11-07)
This is the only evidence that can change the verdict (`REJECT_OR_SUSPEND`, capital ZERO). Nothing in this section authorises capital, and a
good-looking number before the window closes is not a result. Everything below is offline; the one network step is yours.

1. **Save the public responses as they come.** On a machine you control, request
   `GET https://api.bybit.com/v5/market/funding/history?category=linear&symbol=BTCUSDT&startTime=<ms>&endTime=<ms>&limit=200`
   (at most 200 rows a page, ordering unspecified: page by `endTime`) and save each response UNEDITED. Keep them.
   Or let `python3 tools/funding_capture.py --start-ms <ms> --out-dir <NEW dir>` do exactly that loop: one unauthenticated GET per page to the registry host, no redirects,
   each body written byte-for-byte (never overwritten, mode 0600) plus a `manifest.json` with every page's SHA-256 and the gaps on the 8-hour grid (reported, never filled). It is
   never run by tests or CI; you run it. Its pages feed step 2 unchanged.
2. **Make the registered input.** `python3 tools/prospective_prints.py --in page1.json --in page2.json ... --out prints.jsonl`. It converts the
   venue's fraction to basis points itself (never type a unit), refuses anything that is not a clean BTCUSDT print on the 8-hour grid (a symbol that
   moves to a different funding interval is refused: the plan is an 8-hour plan), merges overlapping pages, never overwrites `--out`, and reports gaps
   without filling them. Use `--out` in a new file each time.
3. **Progress, without evaluating:** `python3 tools/carry_prospective.py --funding prints.jsonl`. This records nothing and cannot evaluate.
4. **Evaluate after the window closes (2027-11-07); the closed-window evaluation is the official look, and every look is journaled and counted:**
   `python3 tools/trial_journal.py evaluate --funding prints.jsonl --journal <path on a LOCAL disk> --first-look --allow-unanchored` for the first look,
   then record the printed `ANCHOR TO RECORD NOW` line **off the machine that holds the journal, in a record someone with write access to that machine
   cannot alter** (a printed page, a mail to another person, a commit in another organisation's repository). On every later look pass the anchor with the
   HIGHEST count from that record (`--anchor-n/--anchor-head`, or `--anchor-file` from a copy outside the journal's directory). Be clear about what the code
   can and cannot do: it only refuses an anchor file in the journal's own directory, which is not a trust boundary; a stale anchor verifies a truncated
   journal; and anyone who can write the journal can delete it and rebuild a valid one. The custody is the procedure, not the code.
5. **Read the whole report, not the verdict.** `selection_sensitivity` is NOT a worst case: if settlements are missing, compare `breakeven_fill_bps` with
   the lowest funding a settlement can legally print (you supply it with `--venue-funding-floor-bps`; this repository holds no verified figure). A
   verdict that is "supported" only because of which settlements are present is flagged `DO NOT RELY`. `INSUFFICIENT_POWER` is "not enough data", not "no edge".
6. **Do not change the plan, the coverage floor, the hurdles or the prints after looking.** A different data set is a data revision
   (`--accept-data-revision`), it is recorded permanently in the chain, and it is a different test.

### Owner read-out (offline)
`python3 tools/owner_console.py [--funding prints.jsonl] [--backup FILE]` prints, in one place and without a request or a credential value: whether real money is armed
(`config.is_live_authorized`), the prospective evaluation's progress and the age of the newest print, what capital is (zero until a strategy has an ALLOCATE verdict),
four separate eligibility questions (research / simulated / testnet / owner-authorised), a backup's verification, and the actual-vs-modelled P&L lines. Each section has
one status word: VERIFIED, ESTIMATED, PROVISIONAL, STALE or UNAVAILABLE. UNAVAILABLE is "nothing supplied", never "fine". It exits 3 if the environment arms live.

## Backups: what is not done
Nothing here schedules a backup, stores one off-volume, or has restored one. That needs the owner.

## The testnet drill's own stops
The armed drill (`tools/drill.py --arm`, and the unattended runner that calls it) now refuses, before the first order: a hedge-mode account (the adapter sends no
`positionIdx`; a broker that cannot read the mode also refuses when armed), an existing **kill file** (`touch <run root>/DRILL_KILL` also stops a running drill at its next gate;
the scratch database it runs on cannot hold a kill switch), and a second armed entry on the same UTC day **across processes**
(`--entry-ledger`, required with `--arm`; the unattended runner uses `<run root>/drill_entries.jsonl`; a slot is spent when claimed and not returned if the run fails).
The unattended runner therefore makes at most one armed drill per UTC day. The drill is still off unless you enable it, and nothing here enables it.

## The market-data log: seal, back up, restore-check (owner-run; offline)
The recorder's `md-YYYYMMDD.db` segments are hash-chained inside each file, but nothing outside a file remembered how far it got: deleting the newest records of a segment passed
`MarketStore.verify()` and the writer resumed at the shortened end (reproduced). `tools/md_seal.py` is the outside memory and the tested copy. It opens segments read-only and never
writes into the recorder's directory:

    python3 tools/md_seal.py seal          --dir <MD_DIR> --manifest <OTHER-VOLUME>/manifest.jsonl     # run at least daily; append-only, chained
    python3 tools/md_seal.py check         --dir <MD_DIR> --manifest <OTHER-VOLUME>/manifest.jsonl     # TRUNCATED / MISSING / ALTERED against EVERY earlier seal
    python3 tools/md_seal.py backup        --dir <MD_DIR> --to <OFF-VOLUME-DIR> --receipts <OTHER-VOLUME>/receipts.jsonl --manifest <OTHER-VOLUME>/manifest.jsonl   # refuses if `check` fails; copies only sealed closed days
    python3 tools/md_seal.py restore-check --backup <OFF-VOLUME-DIR> --receipts <OTHER-VOLUME>/receipts.jsonl --manifest <OTHER-VOLUME>/manifest.jsonl   # every sealed closed day needs a matching receipt

`backup` copies only closed days (before today UTC), re-hashes and re-opens each copy and writes a receipt only if it recomputes; a failed copy is set aside as `.REJECTED`, nothing is
overwritten or deleted. A backup is not proven until `restore-check` passes. Keep the manifest and receipts off the recorder's volume and record the printed head somewhere the
recorder's host cannot write (a printed page, another account): the code cannot protect a manifest its own writer can rewrite. The recorder's default retention deletes depth-log
segments after 2 days; do not rely on retention for evidence you have not backed up and restore-checked. Nothing here schedules itself; the schedule and the storage are yours.

**Back up BEFORE retention (operational consequence).** `python3 tools/md_seal.py check|seal ... --receipts <OTHER-VOLUME>/receipts.jsonl` excuses a sealed day that is no longer in the
directory ONLY if all hold: it is older than the oldest segment still present; the receipts verify and hold a receipt for it whose last chain value equals the sealed one; and the oldest
remaining segment's `chain_start` equals that receipt's last chain (a run of pruned days must chain unbroken). `pruned.jsonl` is written by the recorder and is not trusted for this. A day
pruned by the recorder's `--retention-days` BEFORE it was backed up stays a loud failure: `check` says `MISSING ... NOT backed up`, and `seal` and `backup` refuse, because evidence that was
never copied has vanished and nobody should be able to launder that by re-sealing. Therefore: run `seal`, then `backup`, then `restore-check` daily, and keep `--retention-days` longer than
that cycle; pass `--receipts` to `check` and `seal` once retention has started pruning. **A receipt is a claim about a copy, not the copy:** with `--receipts` alone the excuse is receipt-based only, and `check` prints a note saying so; run `restore-check` alongside, or pass `--backup <OFF-VOLUME-DIR>` to `check`/`seal` so each excused day's copy must exist there with the receipted sha256 (missing or different = not excused). If a day was pruned unbacked-up, investigate (is a copy elsewhere?); the manifest keeps reporting it (there is deliberately no automatic way to retire a sealed day: start a new
manifest only as a recorded owner decision). `check` also reports any `md-YYYYMMDD.db` dated after today (UTC) as FUTURE and `seal` refuses it: a fabricated far-future file must not decide
which segment is the newest. The seal manifest, receipts and backup may not be at, under, or a symlink into the recorder's directory.

## The market collector: one run at a time; seal, back up, restore-check (owner-run; offline)
`tools/market_collector.py run-once|seal|check|backup|restore-check|repair-log` take an exclusive non-blocking `flock` on `<out-root>/.lock` for the whole operation (the kernel drops it if the
process dies). A second concurrent `run-once` returns `REFUSED_LOCKED` (no state touched; the first cycle is never renamed to `.INCOMPLETE`); `seal`, `backup` and `repair-log` refuse the same way
with exit 2: retry after the running one finishes. An unexpected capture error mid-cycle is reported as `ABORTED` and the unfinished directory is set aside on the next run.

    python3 tools/market_collector.py seal          --root <ROOT> --manifest <OTHER-VOLUME>/cseal.jsonl
    python3 tools/market_collector.py backup        --root <ROOT> --to <OFF-VOLUME-DIR> --receipts <OTHER-VOLUME>/creceipts.jsonl --manifest <OTHER-VOLUME>/cseal.jsonl
    python3 tools/market_collector.py restore-check --backup <OFF-VOLUME-DIR> --receipts <OTHER-VOLUME>/creceipts.jsonl --manifest <OTHER-VOLUME>/cseal.jsonl

`backup` is bound to the seal manifest and `cycles.jsonl` like `md_seal backup`: it refuses when the root fails its seal or the log does not verify; only sealed, recorded, self-consistent cycles are
copied and each copy must equal the sealed hashes. A cycle skipped because it fails its own manifest, is not in `cycles.jsonl` or is not sealed makes `ok` false (seal first, then back up).
`restore-check` needs a receipt for every sealed cycle. Manifest and receipts may not be at, under or a symlink into the collector's root.

## Execution evidence from the collector: what a maker fill may claim (offline; research only, no credential, no order)
`tools/ms_microstructure.py` loads collector cycles (`load_cycles(root, verify=True)`) into a `MicroDataset`; `ms_fillmodel.place_maker_from_micro / advance_with_trades / taker_from_micro / capacity_from_micro` use it. The default bar policy (`NO_FILL`) is unchanged: a history bar never fills a maker order.
- **Eligibility.** A snapshot is usable at decision time D only if its own receive time is <= D and D minus that time is <= `max_age_ms` (default 5 s; the collector runs once a minute, so a decision must sit just after a cycle). The latest snapshot is the only candidate: invalid or old gives `None` with reason codes from `ds.explain_at(symbol, D)`; a later book is never attached.
- **Reason codes to read.** `CYCLE:HASH_MISMATCH`, `MANIFEST_MISSING`, `COMPLETE_MISSING`, `CHAIN_*`/`LOG_*` (the cycle or log failed verification: restore from backup, see the collector section above), `CROSSED_BOOK`, `NON_MONOTONE_*`, `SYMBOL_MISMATCH`, `DUPLICATE_SYMBOL`, `DISCONTINUOUS` (u/seq regressed), `NON_MONOTONE_TS`, `STALE_AT_RECEIVE`, `CLOCK_SKEW_EXCHANGE_AHEAD`, `STALE_SNAPSHOT`, `FUTURE_SNAPSHOT_NOT_USED`. Nothing is repaired or filled.
- **A maker fill needs queue-depletion evidence.** Queue ahead = visible size at the price at placement x `queue_pessimism`; only recorded opposing-side trades STRICTLY through the price deplete it, only the excess fills. A touch fills nothing. The recent-trade list holds at most `trades_limit` rows, so a file proves coverage only from its oldest trade to its receive time; a longer interval is `TAPE_GAP` (unknown, never "no trades"): the order is closed, nothing fills, the result is `REJECTED`. At a 60 s cadence with `trades_limit=100` a busy symbol will often show `TAPE_GAP`: raise `--trades-limit` (max 1000) or shorten `--interval-ms` before blaming the model.
- **Provenance on every output.** `MEASURED_BOOK_TAPE` (verified collector data), `MODELLED` (the dataset was loaded with `verify=False`, or the markout had no later valid snapshot and is modelled), `REJECTED` (with reasons). `T.Fill.prov` stays `MODELLED`: a simulated fill is never an observed execution.
- **Cohorts.** The collector's books/trades are a NARROW L2 cohort. `cohort_v2` scores |funding|, so `evaluates_funding_edge_ok(ds)` is False for it (and for any unknown or mixed rule); evaluate a funding edge on the broad `market_history` cohort only. The collector records linear books only: a spot hedge leg is `REJECTED` (`NO_RECORDED_BOOK_FOR_CATEGORY`), never priced from the perp book.

## The entry authority: why an opening order is refused, and what you must do (owner)
Every order that can ADD exposure now passes one authority inside `BybitClient._request` (`entry_authority.py`), whoever the caller is: the carry book, `place_order`, the drills, the
linear-stop drill, the unattended runner. A client with no authority refuses (`NO_ENTRY_AUTHORITY`). A reduce-only exit is not gated by it; a spot sell is an exit only if the venue's own position and wallet reads show the short perp stays covered (spot left >= 98% of the short), otherwise it is refused `WRONG_DIRECTION` (unreadable = refused: close the long by hand, it is price risk; a stripped hedge is a naked short). The production book installs
one that checks, in order: the venue, the persistent kill switch (read now; unreadable = engaged), the instrument (only the carry's legs: perp Sell, spot Buy; anything else `UNKNOWN_INSTRUMENT`/`WRONG_DIRECTION`), the order type (exact `Market`/`Limit`; a Market order with a price is refused; a Market order is sized at the mark), your approved risk policy with MEASURED inputs (`risk_policy.py`), the order's notional cap,
and a durable per-`orderLinkId` reservation (an identical resend passes, a different order under the same id is refused, at most 2 distinct unresolved entries).

**Nothing is approved by default, so today the book refuses to open on testnet or mainnet.** The refusal reasons name what is missing: `NO_APPROVED_POLICY` until you write a policy file and
point `RISK_POLICY_PATH` at it (JSON with every `risk_policy.Policy` field and `"approved_by_owner": true`; strict: the string "true" does not count, an unknown or missing field is "no policy");
then `MISSING_INPUT:<name>` for every limit whose value the running book does not yet measure (only `operational_fault` is measured today; see `tools/risk_policy_proposal.py` for the
unmeasured list). That is the intended fail-closed state: do not work around it by editing limits to match what is measured. A loss/hedge/fault breach latches the strategy SUSPENDED in
`risk_latch.json` beside the state database; it survives restarts and clears only by `RiskLatch.clear(strategy, reason=..., at_ms=...)`, which records why. The reservation ledger
(`entry_reservations.jsonl`, same directory) is evidence: do not delete it to "unblock" an entry. Paper and shadow runs send no orders, so they are unaffected.

**Reservation ledger limits (stated, not hidden).** `ReservationStore.resolve()` is **not called anywhere in production**; nothing marks a reservation done. The "at most 2 distinct unresolved
entries" bound is therefore a 15-minute WINDOW over `entry_reservations.jsonl`, not a count of truly open entries, and an old `orderLinkId` stays reserved forever (a different body under it is a
conflict; an identical resend is allowed). An `orderLinkId` must be exactly `[A-Za-z0-9_-]{1,36}` (no whitespace, never stripped) and "identical" means the whole canonical body (category, symbol, side,
qty, orderType, price, reduceOnly, timeInForce). Rows written by an older version lack the type/price fields and so never equal a new order: a resend of such an id is refused, not guessed.
**Writes on any client** are limited to an allow-list (`bybit_connection.WRITE_ENDPOINT_ALLOWLIST`: order create/cancel/cancel-all, position trading-stop/set-leverage, and the demo faucet on the demo venue
only) and a strict canonical path; set-leverage is also bounded (linear, integer 1..10 and, on a client with an authority, no more than `DEFAULT_LEVERAGE` and the approved policy's `max_leverage`, buy == sell, the carry's perp symbol); trading-stop is limited to the exact body the client builds (linear, perp symbol, plain-decimal `stopLoss`, `tpslMode` Full, `positionIdx` 0); cancel needs an `orderId`/`orderLinkId`, cancel-all needs a symbol, and with an authority both are bound to the carry's two instruments. A new write endpoint is a reviewed code change, not a flag.
An order-create body is a CLOSED list of keys (`entry_authority.ORDER_BODY_KEYS`; anything else `UNKNOWN_BODY_FIELD`, a spot Buy with `isLeverage` is a refused margin borrow) and a resend is "identical" only if the whole body matches. `reduceOnly` counts as an exit only as the boolean `true`, exact lowercase `linear`/`inverse`, and (with an authority) only as a perp BUY on the carry's own perp symbol; any other reduce-only order is refused `EXIT_NOT_BOUND:*`. The authority sizes a Market order from the book's snapshot mark only if that snapshot is under 30 s old and perp and spot agree within 5%; otherwise the order is refused (`NO_PRICE_FOR_NOTIONAL`).

**Operator tools that build their own client cannot open an order any more (intended; the authority is not weakened for them).** `tools/linear_stop_venue_drill.py`, `tools/close_testnet_experiment.py` (default client factory),
`tools/testnet_conformance_run.py` builds a bare `BybitClient` with no entry authority, and `tools/drill.py` builds its client through `main.build_bot`, which installs the entry authority only in carry mode with an owner-approved `RISK_POLICY_PATH` (none is committed); without one every opening order they send is refused `NO_ENTRY_AUTHORITY` before the transport. Both also take the single-writer account lock and lease at their command-line entry (see "One writer per Testnet account") (reduce-only exits, cancels,
set-leverage and the stop body still go through, now shape-checked). A testnet run of one of them is therefore an OWNER-run session, and needs all of: (1) an owner-written, approved policy file (`RISK_POLICY_PATH`) with the measured inputs the
book supplies, (2) the tool to install `entry_authority.build_for_book(...)` on its client with the carry's perp/spot symbols, a state directory and a mark provider (a code change per tool, reviewed by you; none has been made), and (3) the usual testnet-only environment. Until then
those tools can run their read-only and exit steps and will report `ENTRY_REFUSED: NO_ENTRY_AUTHORITY` on the first opening order.

## Owner attestation key and registry anchor custody

Two secrets decide whether `strategy_verdict.py` can say QUALIFIED or OWNER_PROFIT_EVIDENCED, and both must live where this repository, its volume and the app host cannot reach.

**The key (`OWNER_ATTESTATION_KEY`).** At least 32 characters with at least 12 distinct characters (a repeated or short string is refused as no key). Generate it on your own machine (for example 32 random bytes, base64), keep it in your own password manager. It never goes in the repository, the Fly volume, Fly secrets, a `.env` the app reads, CI, or a chat. `tools/owner_console.py` reports it as set/unset only and raises a finding if it is set in an environment that looks like the app host (any `BYBIT_*` variable present): if you see that finding, remove the key there and treat it as exposed (generate a new one; old attestations stop verifying, which is correct).

**Attesting evidence (on your machine only).**
`OWNER_ATTESTATION_KEY=... python3 tools/strategy_verdict.py attest --candidate cand.json --evidence evidence.jsonl --registry hypothesis_registry.json --out attested.jsonl`
It signs only observed-stage items (prospective, execution, owner result), and only if `counted()`'s own preconditions hold: bound to this candidate and the REGISTERED spec digest, registered before the observation started, a window not shorter than registered, not in the future. Evidence the engine would refuse anyway is refused at signing. The signature covers the evidence content including `recorded_ms`. Add the signed lines to the registry with `record_evidence`.

**The anchor.** The registry seal is keyless: anyone who can write the file can delete a FAIL and reseal. The anchor is the head digest you hold outside it. Print it with `python3 tools/hypothesis_registry.py --print-anchor`, write it on paper or in an offline note, and store it away from the repository and volume. After EVERY deliberate append (a registration, evidence, an amendment) print and store the new anchor, and keep the old one only as history; pass the current one as `--anchor` when you evaluate. Without it the verdict cannot exceed PROSPECTIVE.

**A changed spec is a new candidate.** The registry stores the spec digest and the cost-chain declarations (fees, slippage, funding, capacity, execution, holding period, eligibility, OOS protocol, parameter grid) at registration. A spec whose digest differs gets INSUFFICIENT_DATA with `SPEC_DIFFERS_FROM_REGISTERED(<what changed>)`. To change anything legitimately, register a NEW candidate id/version and start its ladder again. A registration from before digests were stored reports `REGISTERED_SPEC_DIGEST_MISSING`: its observed evidence is not counted, so it stays below QUALIFIED; re-register it as a new version.

**What they prove, and what they do not.** The key proves that the key holder signed these claims about this candidate and spec. The anchor proves the registry still has the history it had when you recorded the anchor. Neither proves the claims are true: a key holder can sign a falsehood, and nothing here independently checks the exchange, the fills or the account. QUALIFIED means "consistent claims you signed on a registry you anchored", not "verified profit".

## Universe and status capture: what to run in your Codespace and how to read the result

The capture is read-only and unsigned (the `public_collector` role: GET of two allow-listed public paths, no credential), but Bybit geo-blocks some hosts, so YOU run it from your own Codespace, writing OUTSIDE the repository (the tool refuses an output directory inside this repo or any git work tree).

```bash
cd bot
install -d -m 700 ~/datasets
python3 tools/universe_capture.py capture --out-dir ~/datasets/universe-v3-$(date -u +%Y%m%dT%H%M%SZ) --private-root ~/datasets --categories linear
# optionally: --categories linear,inverse,spot   --statuses Trading,PreLaunch,Closed
python3 tools/universe_capture.py verify --dir ~/datasets/universe-v3-<that directory>
python3 tools/universe_capture.py diff <old>/universe-<ms>.jsonl <new>/universe-<ms>.jsonl
python3 tools/universe_capture.py scope --dir ~/datasets/universe-v3-<that directory>     # no network: is it COMPLETE for the declared scope, and if not, the exact blockers (exit 0 complete, 3 not complete, 1 raw integrity failure)
```

`capture` asks for `instruments-info` with no status (the control: what the venue returns by default) and once per status (Trading, PendingOpen, PreLaunch, Delivering, Closed), each cursor-paginated (the venue's percent-encoded cursor is sent back unchanged), then one tickers snapshot. It prints a JSON summary and exits 0 only for `COMPLETE`, 3 for `CONFLICTED`/`PARTIAL`, 4 for `STALE`/`UNVERIFIED`, 2 for a refusal. Every response is stored byte for byte (0600) with its hash; `manifest.json` (schema `universe_capture/v2`) lists them.

How to read it. Each partition has one outcome: `OBSERVED_ROWS`, `OBSERVED_EMPTY`, `REFUSED_BY_VENUE:<code>/<msg>` (the venue said no; this is recorded, not a crash), `TRANSPORT_ERROR:<class>`, or `PARTIAL` (the cursor chain broke: repeated cursor, empty page that names a cursor, a page that repeats an earlier first row, page cap, a later page missing). `delisting_observability` is `OBSERVED` only when the `Closed` partition was answered with a complete cursor chain and every row really was `Closed`; a venue that ignores the status parameter is recorded as `REFUSED_BY_VENUE:status_param_not_honored(...)`, never credited. `dataset_status`: `CONFLICTED` means two different records for one symbol (or one symbolId on two symbols) exist inside the capture, listed under `conflicts` with the differing fields; nothing is merged. `ticker_reconciliation` lists tickers with no instrument in any partition (ORPHAN) and instruments with no ticker; hyphenated dated futures in the tickers are counted under `rejected_tickers`, not fatal. `verify` re-hashes every file and re-derives all of the above from the raw bytes; hand a directory to anyone else only after `verify` says `"ok": true`.

Status enum and the anomalies (rules v2). The live V5 docs (fetched 2026-11-08) list the instrument statuses `PreLaunch`, `PendingOpen`, `Trading`, `Delivering`, `Closed`; `Settling` is NOT in them (a second source reported it, unconfirmed). So the five are the documented, required partitions; `Settling` is asked for as a probe only, and an empty answer is recorded as `UNDOCUMENTED_STATUS_EMPTY` (rows: `UNDOCUMENTED_STATUS_ROWS`) and is never counted toward `required_status_coverage`. Probe ROWS are recorded (raw pages kept, counted) but are EXCLUDED from the universe jsonl and earn no coverage; `scope` lists them under `undocumented_status_rows_excluded` with counts.

Empty and time rules (round 8). An EMPTY capture is never complete: the Trading partition must have rows and the universe must have rows (blocker `EMPTY_UNIVERSE`, `dataset_status` PARTIAL). The "empty list with a blank/absent category echo" anomaly is accepted only for the rare non-Trading partitions (PendingOpen, PreLaunch, Delivering, Closed, Settling probe), never for Trading or the default control. The capture's point-in-time stamp is bound to the bytes: `verify` fails unless `started_ms` is within 5 minutes (`START_BIND_MS`) of the span of the raw pages' server `time` values and `finished_ms >= started_ms`. Plainly: `recv_ms`, `started_ms` and `finished_ms` are self-reported by the capturing host; the venue's server `time` inside the hashed raw pages is the only anchor. A row whose own `status` is none of the six, or is missing, is `UNKNOWN_STATUS` and makes its partition `PARTIAL:UNKNOWN_STATUS`.
- Empty answer with a blank category. The venue answers an empty status partition with `retCode 0`, `list: []` and `result.category` `''` or absent. That is accepted as `OBSERVED_EMPTY` only for a documented status of `linear`, on the first and only page, with no cursor; the page record keeps `category_echo` as `''` or `'MISSING'` (never rewritten to `linear`) and the partition lists it under `anomalies`. A non-empty list with a blank category, any other category, a later page, the default control, a cursor, or `retCode != 0` is not accepted.
- Mixed-status partition. A status-filtered page is complete only when its chain finished AND every row's own `status` equals the request. Rows that differ are kept (the raw page, and the rows in the universe with their real status) and listed under `status_mismatch` (symbol, symbolId, actual status, row sha256, page), reconciled against every other partition, the default control and symbolId lineage: `PARTIAL:STATUS_MISMATCH` when nothing contradicts them (they are `CORROBORATED` by a partition of that status or the default, or `UNCORROBORATED`), `CONFLICTED:STATUS_MISMATCH` when another partition shows a different status, the partition of their own status was observed complete without them, or the symbolId lineage conflicts. If EVERY row differs the venue ignored the parameter (`REFUSED_BY_VENUE:status_param_not_honored`). The default control must also agree with the `Trading`/`PendingOpen` partitions (`CONFLICTED:DEFAULT_CONTROL`).
- `scope` re-derives all of this from the raw bytes (the manifest is never trusted; a manifest written before rules v2 is judged from its bytes and its stale claims are listed under `legacy_claim_differences`). The declared scope is "linear USDT perpetual lifecycle universe": COMPLETE only when integrity holds, the default control and all five documented statuses are complete, nothing is conflicted, `delisting_observability` is `OBSERVED`, there are no ticker orphans and `dataset_status` is `COMPLETE`. A PARTIAL or CONFLICTED capture stays so; the fix is a new capture, never an edit.
- Lifecycle classes (rules v3). A status-filtered partition may legitimately carry rows whose own status differs: the owner's `status=Closed` held two dated `LinearFutures` rows and three `LinearPerpetual` rows whose own status was `PendingOpen` with a historical `deliveryTime`. `classify_lifecycle(row, requested_status=, server_time_ms=, observed_in=, evidence=)` gives each row ONE class: `OUT_OF_SCOPE_DATED_FUTURE` (not `LinearPerpetual`: counted, never an error), `CONFIRMED_CLOSED_PERPETUAL` (Closed, deliveryTime at or before the page's server time), `CONFIRMED_CANCELLED_BEFORE_OPENING` (terminal pending-open perpetual AND caller-supplied evidence from VERIFIED history datasets: `funding_rows == 0`, `kline_rows == 0`, `coverage_complete` true), `TERMINAL_UNRESOLVED_PENDINGOPEN` (the same without that evidence: a past deliveryTime and absence from tickers or from the live PendingOpen partition prove nothing and never promote a row to cancelled), `UNEXPLAINED_PARTITION_CONTRADICTION` (another partition, the default control, symbolId lineage or history says otherwise, or the status is unknown/missing; a pending-open perpetual WITH funding or kline rows traded), plus `ACTIVE_PERPETUAL` and `OUT_OF_SCOPE_OTHER_CONTRACT` (a non-USDT perpetual). Every mismatched row keeps `query_status` (the partition asked) and `returned_status` (its own status) separately, with its row sha256; the raw page bytes are never edited and no row is relabelled or dropped.
- When EVERY mismatched row of a partition is explained (dated future, other contract, terminal pending-open) the outcome is `PARTIAL:STATUS_MISMATCH_EXPLAINED` with per-class counts (`status_mismatch.by_lifecycle_class`) and `dataset_status` is `COMPLETE_WITH_EXPLAINED_MISMATCH`; the partition is still not clean, `delisting_observability` stays `NOT_OBSERVED`, `complete_for_scope` stays false and those blockers carry `explained: true`. Any unexplained row keeps `CONFLICTED:STATUS_MISMATCH` and blocks. `scope` adds `eligible_for_research`, `research_blockers`, `lifecycle` (class counts and the notable rows) and `eligible_perpetual_lifecycle_universe` (the set usable for research: Trading perpetuals and confirmed-closed ones with a stated window; never cancelled, unresolved or out-of-scope rows). `eligible_instruments(path, history_evidence=None)` is the one function planners, loaders and the control centre call; it is a view of `scope`, so `verify`, `scope` and `eligible_instruments` report identical class counts. A capture written under older rules is judged from its raw bytes (`legacy_manifest`), never edited.

What the `Closed` partition can and cannot prove. It shows only the instruments the venue still serves with that status today. It can establish that those instruments were delisted/expired as of this capture, with their last published rules. It cannot show instruments the venue has dropped entirely, it says nothing about the history before your first capture (which is NOT point-in-time verified), and an empty or refused `Closed` partition proves nothing about whether delistings occurred. Point-in-time evidence only starts from the first verified capture; repeat the capture on a schedule and use `diff` to see listings, status transitions, symbol renames (same symbolId, new symbol) and changed tick, lot, leverage, funding-interval and cap rules.

## Historical and continuous market data: what to run in your Codespace and how to read it (owner; offline tests, no credential, no order)

Everything below is PUBLIC data fetched with unsigned GETs through the `public_collector` role (`tools/market_history.py`, `tools/market_collector.py`); nothing needs a key, `.env` or a Fly secret, and none of it can place an order. Bybit geo-blocks some hosts, so YOU run it from your own Codespace; the agent that wrote it has never run it against the exchange (its tests inject a scripted venue). All data goes under ONE private root OUTSIDE Git (the tools refuse a root inside any git work tree, a link, or a group/world-readable directory). Report the JSON outputs back; do not paste them into the repository.

```bash
cd bot
export ROOT=~/datasets/md-$(date -u +%Y%m%d) ; install -d -m 700 ~/datasets ~/seals ~/backups "$ROOT"
export UNI=<the universe capture directory from the section above, verified: python3 tools/universe_capture.py verify --dir $UNI>
```

**1. Spot leg (is there a Bybit spot pair for a perp?).** One request, `category=spot`, no pagination.
`python3 tools/market_history.py spot-instruments --out-root ~/datasets/spot-snap`  -> prints `dir` (`~/datasets/spot-snap/spot-instruments/snapshot-<ms>`, where `make` looks for it), `rows`, `by_quote`, `by_status`; exit 0 only if `dataset_status` is `COMPLETE`.
`python3 tools/market_history.py hedge-availability --universe-capture $UNI --spot-dir ~/datasets/spot-snap/spot-instruments/snapshot-<ms> > $ROOT/hedge.json` (no network). Per perp: `SPOT_TRADING`, `SPOT_NOT_TRADING`, `NO_SPOT_PAIR`, or `UNRESOLVED_MULTIPLIER` (a 1000x contract such as 1000PEPE: the unit ratio is not in the data, so it is never assumed hedgeable).

**2. Bounded initial backfill, funding for the whole eligible universe** (live AND Closed contracts; a Closed contract is asked up to its `deliveryTime`; a contract delisted before the window is listed under `excluded`, not counted as missing).
`python3 tools/market_history.py funding --out-root $ROOT --universe-capture $UNI --include-statuses Trading,Closed --days 400 --workers 2 --rate 5`
Expect roughly 890 Trading + 318 Closed symbols, ~7 requests each at a shared 5 requests/second (about half an hour). It is resumable per symbol: if the run stops (Ctrl-C, a 429 storm, a lost connection), run the SAME command again; verified pages are never fetched twice, a torn or corrupt page is moved to `<SYMBOL>/quarantine/<n>/` and refetched. Exit 0 only when the whole dataset is `COMPLETE`; any other status exits 1 (read the manifest, do not retry blindly).

**3. Klines for a chosen window, and open interest.** `--start-ms/--end-ms` (epoch ms) or `--days N`; `--symbols A,B` or the universe flags.
`python3 tools/market_history.py kline       --out-root $ROOT --universe-capture $UNI --include-statuses Trading --interval 60 --days 30`   (trade-price klines, interval in minutes or D/W)
`python3 tools/market_history.py mark-kline  --out-root $ROOT --universe-capture $UNI --include-statuses Trading --interval 60 --days 30`
`python3 tools/market_history.py index-kline --out-root $ROOT --universe-capture $UNI --include-statuses Trading --interval 60 --days 30`
`python3 tools/market_history.py open-interest --out-root $ROOT --universe-capture $UNI --include-statuses Trading --interval 1h --days 30`   (`5min,15min,30min,1h,4h,1d`)
Each dataset is `$ROOT/<dataset>[-<interval>]/` with `manifest.json`, one directory per symbol (raw `page-NNNNNN.json`, `pages.jsonl`, `rows.jsonl`).
Without `--end-ms`, kline/mark/index/open-interest default the window end to the LAST CLOSED candle boundary (`floor((now - 60s)/interval)*interval - 1`, weekly candles on Monday) so the forming candle is never requested and the capture is not permanently PARTIAL (`unclosed_candle`); the manifest records `request.window_end_basis` (`LAST_CLOSED_BOUNDARY`, `CLOCK_NOW` for funding, or `OPERATOR_END_MS` for an explicit `--end-ms`).

**3b. A legitimate funding interval change (`unproven_regime_change`).** Bybit changes a contract's funding interval (480 -> 240 -> 60). The collector records each such regime in `segments`/`regime_changes` and normalises per segment, but marks the symbol PARTIAL `unproven_regime_change` unless the operator corroborated that exact change: a head run at 2x/4x/8x the declared interval looks the same as a genuine change and hides missing prints. First check the instrument's interval history (Bybit announcements / the instrument record at the dates in `regime_changes[].at_ts`). Then preview: `python3 tools/market_history.py verify --dir $ROOT/funding --accept-regime-change BTCUSDT:480:240 --accept-regime-change BTCUSDT:240:60` prints `status_if_accepted` (a preview only; `ok` and the manifest do not change). To record the acceptance, re-run the SAME collection command with the same `--start-ms/--end-ms` (the manifest's `request`) plus the same `--accept-regime-change SYMBOL:from_min:to_min` flags: the resume reuses the verified raw pages (no refetch), stores the acceptance in each symbol's `spec`, and verify then re-derives COMPLETE. Every change in a ladder needs its own flag; a flag for a change that did not happen does nothing. If the history does not corroborate the change, leave the symbol PARTIAL.

**4. Verify (pure Python, no network).** `python3 tools/market_history.py verify --dir $ROOT/funding` re-hashes every raw page, re-derives every row, gap and status from the bytes and compares with the manifest: `"ok": true` or a list of problems (`PAGE_HASH_MISMATCH`, `PAGE_MISSING`, `UNLISTED_FILE`, `rows.jsonl hash differs`, ..., `LEDGER_CHAIN_BROKEN` (a page's request `endTime` is not the previous page's `next_end`: a page was dropped, reordered or edited out of the walk; the symbol is UNVERIFIED), ...). Run it before you hand a dataset to anyone.

**How to read `dataset_status`** (per symbol in `symbols.<SYM>.status` with `reasons`; the dataset is the worst symbol). `COMPLETE`: pages verified, no gap, head reaches the window start (or the contract's launch), tail within two intervals of the end. `STALE`: complete but the newest row is older than two intervals before the end. `PARTIAL`: a known hole or unfinished run: `gaps`, `off_grid_step`, `head_gap`, `head_unverified_no_launch_time`, `rejects`, `clock_skew`, `not_terminated` (page cap/429/network: rerun), `interval_disagrees_with_record`, `unproven_regime_change` (the data shows a funding interval change, e.g. 480 -> 240 -> 60, that the operator has not corroborated: spacing alone cannot tell a genuine change from a missing head, e.g. a head at 8h under a declared 60 min is 62% missing prints, so the symbol is never COMPLETE until accepted; see section 4), `regime_flapping` (an interval that comes back non-adjacently, such as 240/480/240/480: prints are hidden between the runs), `unclosed_candle` (a kline/mark/index/open-interest row whose interval had not ended at the server's own time: it is dropped from `rows`, listed in `unclosed_candles`, and a window whose newest candle is still forming is PARTIAL until a later run), `no_rows`. `CONFLICTED`: one timestamp with two different rows (nothing is merged). `UNVERIFIED`: a page failed its hash, or the funding interval is unknown (the grid check is REFUSED, never defaulted to 480). Funding intervals differ per symbol (480/240/60 minutes) and can change inside a symbol's history (a regime is a sustained run of >= 3 equal spacings whose interval divides a day and is not a whole multiple of the interval before it, unless the instrument record declares it; three 16h or 24h steps inside an 8h grid are missing prints, reported as `gaps` and PARTIAL, never a regime; the same holds for a HEAD run that is a whole multiple of the declared interval and is directly followed by a run at the declared interval. Only a multiple that is NOT a power of two counts (real funding intervals 480/240/120/60 change by powers of two), so a genuine direct 480 -> 240, 480 -> 60 or 240 -> 60 change is kept as a regime; residual limit: a head hole that is exactly a power-of-two multiple of the declared interval cannot be told from such a genuine change by spacing alone): `segments` lists each regime with `fundingInterval_min` and `settlements_per_day`, `regime_changes` lists where it changed, and neither is a gap. `coverage` carries `requested_window` and `served_first_ts/served_last_ts/served_rows`: the venue may serve less than a contract's whole life, and that is recorded, never assumed. Every symbol also carries `gaps` (never filled).

**The seven timestamps** (documented at the top of `tools/market_history.py`): `exchange_event_time`, `source_server_time`, `local_receive_time`, `collection_time`, `normalization_time`, `observation_time` (earliest instant a row may be used: a kline is final at start+interval) and `decision_time` (the consumer's; never earlier than `local_receive_time` or `observation_time`). `market_history.usable_at` / `check_time_invariants` are provided as a library check; the ranked-funding evaluator is the only verdict-path consumer, so the rules are enforced where the evaluator is used and nowhere else. Network note: `urllib` honours `HTTPS_PROXY`/`NO_PROXY`; behind a proxy, the proxy sees these public requests (the host/path allow-list is checked on the URL, not the route).

**5. Continuous collection** (order books and recent trades only for the top-turnover screening cohort `turnover24h_desc_symbol_asc_v1`; funding/klines/OI above are separate and cover the whole universe).
`python3 tools/market_collector.py run-continuous --out-root $ROOT --interval-ms 60000 --duration-s 86400 --stop-file ~/datasets/STOP --max-symbols 20 --seal-manifest ~/seals/md-manual-seal.jsonl --seal-every 60 --backup-to ~/backups/md-manual --receipts ~/seals/md-manual-receipts.jsonl --backup-every 60 --restore-check-every 360`
Stop it cleanly with `touch ~/datasets/STOP` (remove the file before restarting). Restart it with the same command after a crash or reboot: an interrupted cycle is set aside as `.INCOMPLETE`, the downtime is recorded as a gap. It refuses (health `REFUSED`) when free space is under `--reserve-bytes` (default 1 GiB), the root is inside Git or not 0700, the cycle log needs your attention (`repair-log` is the documented repair), or after `--max-consecutive-failures`. `$ROOT/health.json` (rewritten every cycle, 0600) holds: `status`, `stop_reason`, `last_cycle`, `gaps`, `consecutive_failures`, `disk`, `last_seal`, `last_backup`, `last_restore_check`, `hook_cadence_ms`, `rate_limit_events_total`, `refusal`. A hook that fails for any reason is recorded in its `last_*` entry and collection continues; an unexpected crash of the loop writes `status: CRASHED` with the reason before the process exits.

**6. Seal, back up, restore-check by hand** (same tools the loop calls; the seal manifest and receipts must live OUTSIDE `$ROOT`):
`python3 tools/market_collector.py seal --root $ROOT --manifest ~/seals/md-manual-seal.jsonl`
`python3 tools/market_collector.py backup --root $ROOT --to ~/backups/md-manual --receipts ~/seals/md-manual-receipts.jsonl --manifest ~/seals/md-manual-seal.jsonl`
`python3 tools/market_collector.py restore-check --backup ~/backups/md-manual --receipts ~/seals/md-manual-receipts.jsonl --manifest ~/seals/md-manual-seal.jsonl`   (`"ok": true` is the only proof the backup restores)
Copy `~/backups/md-manual`, the receipts and the seal manifest to a second place you control (another disk or machine); a copy beside the original is lost with it. The history datasets are re-hashable with step 4; back them up by copying `$ROOT/<dataset>` after `verify` says ok.

**7. Freshness audit** (read-only; this is NOT the `carry-watch` workflow, which watches the Fly monitor history).
`python3 tools/data_freshness_audit.py --root $ROOT --research-universe ~/research-universe.json --universe-capture $UNI --backup-dir ~/backups/md-manual --receipts ~/seals/md-manual-receipts.jsonl --seal-manifest ~/seals/md-manual-seal.jsonl > ~/audit.json; echo $?`
`~/research-universe.json` is `{"symbols": ["BTCUSDT", ...]}` or one symbol per line. Output has three separate axes: `code_correctness` (always `NOT_ASSESSED` here: that is CI's question), `data_freshness` and `research_readiness`. `data_freshness`: `NO_DATA` (exit 4; never healthy), `STALE` (exit 3), `PARTIAL` (exit 1: a gap, a dataset that is not COMPLETE or does not re-hash, a failed or never-run backup/restore-check, a skipped verification), `HEALTHY` (exit 0: real complete data whose history window ended within `--history-max-age-ms` (default 3 days), AND a backup, a restore-check and a seal that THIS run verified live (all of `--backup-dir --receipts --seal-manifest`) and that are younger than `--ops-max-age-ms` (default 3 days; the cadence the collector records in `health.json` can only tighten it); older ones are `STALE`). `health.json` is unauthenticated: an ok record in it without a live check is reported as `*_CLAIMED_NOT_VERIFIED` (PARTIAL) and never makes HEALTHY. A damaged receipt/seal file is reported as a failed check (exit non-zero), never a traceback. Data stamped later than the audit clock plus 5 minutes (a wrong audit clock, a skewed host, a forged row) is `DATA_FROM_THE_FUTURE` (PARTIAL): a negative age is never freshness; fix the clock or find the row before trusting the verdict. A seal-manifest row whose body is hand-made or damaged (a cycle entry that is not an object, lacks `manifest_sha256`/`files`, has a path-shaped name, or a `log_cycles` that is not a list of strings) is `MALFORMED_SEAL_ROW` in `market_collector.py check` (exit 1); a `cycles.jsonl` row whose `cycle` is not a plain non-empty name (a list, dict, number, path) is `MALFORMED_LOG_ROW` (exit 1; `seal` refuses; never a traceback); `seal` refuses over it, and no `market_collector.py` command prints a traceback (exit 2 with a one-line message). `research_readiness`: `READY` only when every declared symbol is COMPLETE in every dataset present, all status partitions (Trading, Closed, PreLaunch) were answered by the venue in the universe capture, and nothing is UNVERIFIED/CONFLICTED. A first run on a fresh root is expected to be `NO_DATA` or `PARTIAL`; that is the tool working.

What none of this proves: that the bytes came from the exchange (a hash proves what was read, not who produced it), that nothing is missing before a contract's recorded launch, or that history before your first universe capture is point-in-time. It selects nothing by performance and fills nothing.

## Full-universe history for the ranked-funding design: plan, backfill, cohort, diagnose (owner; offline tools, public GETs only, no credential, no order)

Why this exists: a ranked-funding run that loaded 9 symbols and zero of the 60 required non-overlapping 7-day holding rows is missing (a) history for the whole eligible universe and (b) a stated reason. `tools/backfill_plan.py` computes what is needed and what is missing; `market_history.py --symbols-from-plan` then collects EVERY dataset for the SAME symbols. The agent that wrote these tools never saw your data or the exchange; you run them. ## Multi-symbol authority and the disabled testnet adapter (owner; offline, no credential, no order)

What exists: `tools/ms_risk.py` (portfolio risk gate), `tools/ms_accounting.py` (ledger with provenance), `tools/ms_economics.py` (breakeven, stress, leverage ceiling), `tools/ms_authority.py` (`MultiSymbolAuthority`, the entry authority for the multi-symbol layer at the final venue-request boundary) and `tools/ms_testnet_adapter.py` (a DISABLED capability description). None is wired into `main.py` or any production path. The BTC carry's `entry_authority` is a different object and is unchanged.

**It is not installed anywhere.** `ms_authority.install(client, authority)` is an explicit call and refuses unless `client.transport` is the very transport the authority was built for and `client.venue` equals the policy venue. The authority itself refuses to be built on anything but an in-process simulation, and "simulation" is a WHITELIST of concrete classes, not an attribute a class can claim: `backtest.SimulatedExchange`, `ms_pipeline.SimulatedTransport`, or a class passed to `ms_authority.register_simulated_transport(cls)` (exact class; refused if it derives from `RequestsTransport`/`CapabilityTransport`, or if it or its module touches urllib/http/requests/socket/websocket/ssl). An instance holding a network or session object under any attribute name is refused even when registered. `IN_PROCESS_SIMULATION` is no longer consulted. A real HTTP transport, an unregistered transport and a capability-wrapped one are refused with `TRANSPORT_NOT_SIMULATED:...`. Registration is a statement in code a reviewer reads; it is not a sandbox (a registered class could still hide a connection in a function body).

**Reading a refusal** (`OrderNotSent: ENTRY_REFUSED: <codes>` from the client; the codes are stable):
- `GROUP_NOT_REGISTERED`, `LEG_NOT_IN_GROUP`, `ORDER_LINK_ID_NOT_GROUP_LEG`: the order is not exactly one leg of a risk-approved group. `orderLinkId` must be `<group_id>-<leg_id>`; ids are `[A-Za-z0-9_]` only, the whole link at most 36 characters.
- `BODY_FIELD_NOT_PLAN:<field>`, `UNKNOWN_BODY_FIELD:<key>`: the wire body differs from the registered leg, or carries a key the plan does not state (`isLeverage`, `positionIdx`, `marketUnit`, trigger and take-profit fields are never sent).
- `RISK:<code>`: `ms_risk.risk_assess` refused the group's remaining legs on top of the account and every other pending reservation. `ACCOUNT_DATA_STALE` / `MARKET_DATA_STALE` / `BOOK_STALE:<sym>`: the account read or book is older than the policy allows; refresh it, do not raise the limit. `*_UNKNOWN`: an input was missing or None and was NOT read as zero.
- `VENUE_NOT_ALLOWED`: the client named a venue other than the policy's sandbox venue (`mainnet`, `eu`, an unknown or mis-cased name are all refused).
- `KILL_SWITCH_ENGAGED` / `KILL_SWITCH_UNREADABLE`: an engaged or unreadable switch stops every NEW entry. Exits are not blocked by it.
- `RESERVATION_CONFLICT_SAME_ID_DIFFERENT_ORDER`: the same `orderLinkId` was reserved for a different order. An identical resend is allowed (that is how a lost acknowledgement is resolved). Reconcile with the venue before any resend.
- `GROUP_LEDGER_UNREADABLE`: `ms_groups.jsonl` in the state dir has a bad line. The authority refuses rather than guess what was registered.
- `EXIT_*`: a reduce-only exit must be on a symbol the group opened, the opposite side, link `<opened_group_id>-<new_leg_id>`, and is bound by QUANTITY, never by notional: each exit at most 1.02 x the entry leg, and CUMULATIVELY per group and symbol (`EXIT_CUMULATIVE_QTY_EXCEEDS_ENTRY`): every approved exit reserves its quantity in the durable ledger (an identical resend is idempotent, the same link with a different order is `EXIT_LINK_CONFLICT`). A Limit exit must be within 10% of the current mark (`EXIT_PRICE_OUT_OF_BAND`; an unreadable mark is `EXIT_PRICE_UNVERIFIABLE`; use a Market reduce-only exit). A spot SELL is an exit only when the venue's own reads (`hedge_reader`) show the perp stays covered; otherwise `SPOT_SELL_NOT_PROVEN_HEDGE_KEEPING`. **An exit that did not fill must be released** (`release_exit(order_link_id, unfilled_qty=None)`): only a link with an OPEN reservation can release anything, a bare call gives back just the unfilled remainder (never quantity recorded as filled via `record_exit_fill`), the pipeline releases a refused exit only when that very call made the reservation (never on `EXIT_LINK_CONFLICT` / `EXIT_LINK_RELEASED`), a filled quantity stays consumed, an unfilled one stays reserved until released, and a caller that never releases rejected or cancelled exits will eventually be refused every further exit. `ms_risk` applies the same rule per plan against the quantity the account holds (`REDUCE_EXCEEDS_POSITION`, summed over every reducing leg of the plan, the whole plan refused; the position may state its own `qty`, otherwise it is notional / mark) and the same 10% band (`EXIT_PRICE_OUT_OF_BAND`).

**Pending reservations.** A registered group reserves ALL of its legs, sent or not, from `register_group` until each leg is settled with `settle_leg(group_id, leg_id)` (the account's own position read shows it) or the group is closed with `resolve_group(group_id)` (flat per the venue's read). Priority is registration order: a group is judged on top of every EARLIER unresolved group's legs and never against a later one's, so a later group that does not fit is refused at registration and cannot squeeze an in-flight group between its legs. Forgetting to settle is conservative (the exposure is counted twice); an abandoned registered group blocks later groups until you `resolve_group` it. `ms_risk` also refuses an inconsistent position (`POSITION_KEY_CATEGORY_MISMATCH`: a `SPOT:` key must be category `spot` and the reverse) and a spot sell without positive inventory (`SPOT_SELL_WITHOUT_INVENTORY`: a missing, zero or negative figure is not inventory; the sell may not exceed the held quantity).

**The disabled testnet adapter.** `python3 tools/ms_testnet_adapter.py generate --candidate-id ID --spec-digest HEX --symbols BTCUSDT,ETHUSDT` prints the exact action manifest: explicit symbol and strategy allow-lists, one AGGREGATE notional ceiling of $500 across ALL symbols (never per symbol; the Testnet session's own ceiling since 2026-11-09, independent of the shared `shadow.SHADOW_MAX_NOTIONAL_USD` = $100 that still caps the frozen BTC experiment, the drills and the live-gate tests), gross/net/unhedged/active-group/leverage/age bounds, the persistent kill-switch file semantics (`MS_KILL` present = stop; unreadable = stop), the reconciliation rules, the reduce-only recovery plan, the evidence list and the DEDICATED credential variable names (`BYBIT_API_KEY`/`BYBIT_API_SECRET` are refused). Authorisation is always `NOT_GRANTED`. Bounds can be lowered, never raised: the validator refuses a manifest above any ceiling. `validate FILE` checks a manifest; `status` reports whether the owner capability file exists (it does not in this repository, so `enabled: false`).
This module contains no code that sends an order or opens a connection (a test parses it). Even if you create the capability file (`~/.ai-agent-control/ms_testnet_capability.json`: `{"schema": "ms_testnet_capability/1", "manifest": <authorised manifest>, "manifest_plan_sha256": <its digest>}`), nothing is sent. **The file is SELF-ATTESTED:** nothing can prove a human wrote it (any process running as the same user can write a granted manifest and its digest, and the digest is not a signature). The check is that it is a regular, non-symlink file OWNED BY THE CURRENT USER with mode 0600 (no group or world bits, so never group- or world-writable), judged on the descriptor that is read; anything else is refused (`CAPABILITY_FILE_NOT_OWNED_BY_CURRENT_USER`, `CAPABILITY_FILE_MODE_NOT_OWNER_ONLY_0600`). Treat it as one signal among several, not as the owner's signature: the flag is only one of the three conditions `ms_authority` requires before it can be bound to a non-simulated transport (the others: the sandbox venue `testnet`, and a dedicated testnet credential name on a `TESTNET_EXECUTOR` capability transport). Nothing in this repository builds that transport for it. Do not create the file, and do not touch `carry-drill-testnet.yml` or `CARRY_DRILL_ENABLED`, until you have decided to run a bounded testnet qualification yourself.

**What none of this proves.** That any candidate has edge (`ms_economics.assess` returns `PASS` only when every input's provenance is MEASURED / VENUE_STATED / DERIVED / MODELLED, both the base and the pessimistic scenario are positive, AND four evidence caps are lifted: the pessimistic factors' `scenario_prov` is not ASSUMED (the built-in factors are ASSUMED, so by default `assess` cannot PASS: pass `pessimistic_prov` only for factors you grounded in measurement); no zero tail probability (operational failure, liquidation, a maker that always fills) unless MEASURED with `n_samples` > 0 (`ZERO_TAIL_PROBABILITY_NOT_MEASURED:<input>`); and the expected funding is not in-sample (`EconInputs.funding_is_in_sample` defaults to True and forces NOT_PROVEN; a funding input labelled DERIVED or whose `basis` says TRAILING_IN_SAMPLE never supports PASS). PASS is a necessary condition for edge, never a sufficient one, and it cannot tell whether the inputs are right), that the ledger's P&L is the venue's (`status: RECONCILED` and `claimable_profit` mean INTERNAL CONSISTENCY: flat per the ledger's own fills and every component known; they are not a venue read. Each report carries `reconciliation_basis` (`INTERNAL_CONSISTENCY_ONLY` unless a venue position read was injected), `internally_consistent`, `venue_reconciled` and `venue_claimable_profit`; the last two are set only by `Ledger.pnl(venue_positions={"SYMBOL": qty, "SPOT:SYMBOL": qty})` when that read matches every ledger position. A ledger with open or unknown legs reports `claimable_profit: None`), or that a simulated transport behaves like the venue.
## Multi-symbol replay and paper

Scope: `tools/ms_portfolio.py`, `ms_fillmodel.py`, `ms_execution.py`, `ms_replay.py`. REPLAY and PAPER ONLY, with a simulated transport; nothing here can reach a venue, and the old BTC production path (`carry_engine`, `carry_broker`, `entry_authority`) is untouched.

**What a result means.** Every fill is `MODELLED`/`SIMULATED`. A replay report (`ms_replay.build_report`) always carries `promotion_eligible: false` and lists `promotion_blockers` (modelled fills are not execution evidence; assumed inputs such as a synthetic book or defaulted instrument filters; fewer than 30 INDEPENDENT observations). Overlapping round trips are counted once (`observations.independent` vs `closed_round_trips`); never quote the larger number as evidence. The confidence interval `ci95_independent_net_bps` has a trial-adjusted twin (`lo_adj`/`hi_adj`): widen by the number of variants ever tried, which `ms_replay.record_trials(path, keys)` keeps in a persistent append-only ledger (keep it outside `runs/` and outside Git; a report with `persistent_ledger: false` UNDERSTATES the search).

**Fill model.** A post-only order fills only when the opposite side trades strictly THROUGH its price for more than the queue ahead (visible size at the price x `queue_pessimism`). A touch is not a fill. With bars but no trade volume (the market_history capture has none) the default `bar_policy="NO_FILL"` fills nothing; `ASSUME_THROUGH_MULT` is an explicit, ASSUMED optimism knob and the report says `BARS_FROM_MARKS_NO_TRADE_VOLUME`. Fees: maker 2.0 bps (modelled), taker 5.5 perp / 10.0 spot (carry_costs); rebates are never assumed.

**Lifecycle incidents** (`ms_execution`, journal = hash-chained jsonl; verify with `ms_execution.verify_chain(store.read())`; a broken chain makes the engine refuse to start):
- `UNKNOWN_OUTCOME` (lost ack, or a restart with an order intent that has no ack): do NOT resubmit by hand. `engine.reconcile(now_ms)` reads the venue by `orderLinkId = group_id-leg_id`; an order found is adopted, only a COMPLETE read showing no order after `resend_after_ms` authorises one idempotent resend.
- Fills adopted from an order's cumulative quantity (`recon:<link>:<cum>`) are REPLACED, not added to, when the real executions later arrive: `leg.filled` never exceeds what the venue shows.
- Spot flat check: a spot balance includes what the client already owned. The engine records a per-key baseline (venue minus expected, from a COMPLETE read) before a group sends its first order and verifies the DELTA at close. No baseline (`SPOT_BASELINE_MISSING` anomaly) means the group stays `EXITING` and is never closed on a guess; a real residual delta is `NOT_FLAT_ON_VENUE`.
- Halt reasons in `engine.halts` stop NEW exposure only (exits and reduce-only unwinds still run): `UNKNOWN_VENUE_POSITION` (lifts itself only on a position read that is both present AND `complete`; an incomplete read never lifts it), `POSITION_MISMATCH:<key>`, `UNATTRIBUTED_FILL`, `RISK_BREACH:*` (manual `resume_new_exposure`).
- `CLOSED` is reached only when the venue's own position read agrees with the journal; otherwise the group is `EXITING` or `HALTED` with `NOT_FLAT_ON_VENUE`.
- A late fill after cancel/close re-opens the group as `UNHEDGED` and it is unwound with a reduce-only taker order.

## Multi-symbol pipeline and control-centre artifacts (offline; replay and paper only; no credential, no order)

Scope: `tools/ms_pipeline.py` (`run(...)`) wires the scanner, allocator, risk gate, authority, lifecycle engine, simulated venue, fill model and ledger into one run and writes the six artifacts the control centre displays plus `pipeline_summary.json` and `reconcile_report.json` (eight files; the control centre reads all eight). It sends nothing: the order sink is `ms_execution.SimVenue`, the authority is bound to an in-process simulation transport, and the module has no client, credential, network or wall clock (`generated_ms` and the PAPER clock are arguments). `tests/test_ms_pipeline.py` is the proof that the stack works together, including mutation tests that break one behaviour at a time.

**The command line** (`python3 tools/ms_pipeline.py {validate|run} ...`, offline; exit 0 = ran, exit 2 = refused with `{"ok": false, "error": {"code", "message"}}` on stdout and nothing written). Every input is explicit and checked BEFORE anything runs: `--history-root`, `--universe-dir`, `--spot-dir` (all three re-verified by the real verifiers; an unverified or tampered dataset is `INPUT_NOT_VERIFIED`), optional `--collector-root`, `--artifacts-dir` (must be NEW or EMPTY, outside git, never an input dataset, no symlink), `--ledger-dir` (persistent; holds `candidate_competition`'s multiple-testing ledgers and `ms_pipeline_trials.jsonl`; never under `bot/state`, git, the artifacts or a dataset), `--start-ms/--end-ms` (epoch ms, start before end, at least one hold long, overlapping the verified history), `--candidate` (a file under `research/candidates`, or any file with `--candidate-digest`; families this pipeline cannot run are `CANDIDATE_NOT_RUNNABLE`), `--execution-policy MAKER_FIRST|TAKER`, exactly one of `--risk-policy FILE` (ms_risk's closed schema; must name the same candidate and spec digest and list every verified symbol) or an explicit `--derive-risk-policy`, `--mode REPLAY|PAPER`, `--clock-ms` (the stamp; default the window end; the wall clock is never read) and `--code-revision` (default `git rev-parse HEAD`, else `UNKNOWN`; never invented). `TESTNET` is refused (`MODE_NOT_ACCEPTED`: testnet sessions belong to the owner-invoked `ms_testnet_*` tool); there is no mainnet mode and no flag for one. `--collector-root` is refused with `COLLECTOR_PATH_UNAVAILABLE` while `ms_microstructure` is not in the tree: it is never silently ignored. `validate` prints the input digests and the candidate and writes nothing.

**Reconciliation, loss limits, collector.** After EVERY replay / paper step the pipeline runs `ms_reconcile.reconcile` (the venue's own position read is the reference; engine, portfolio, ledger and the authority's reservations must agree) and `HaltOnDisagreement.for_engine(engine)` halts new exposure on any finding (exits continue; nothing is overwritten). The outcome is `reconcile_report.json` (`reconcile_report/v1`: `identity`, `findings` [`code`, `key`, `views`, `detail`], `halt_new_exposure` at the end of the window, `reasons`, `compared`, plus `history` of every finding raised at any step, `n_steps_checked`, `ever_disagreed`); any disagreement makes the summary say `UNKNOWN_OR_UNRECONCILED`. The displayed net is `Ledger.canonical_net()` and is `null` while any component is unknown. `--max-daily-loss-usd` / `--max-drawdown-frac` (default: the portfolio policy's 0.10) set ms_risk's hard limits on the derived policy and the allocator's; the replay state carries `equity_usd`, `day_start_equity_usd` (equity at the first step of the UTC day) and `peak_equity_usd`, and ms_risk refuses every entry when one is unknown. With `--collector-root` the verified `ms_microstructure` dataset gives MEASURED decision-time books and the tape windows whose coverage the tape proves; symbols without a recorded book are excluded, a funding-selected cohort (cohort_v2) is refused (`COLLECTOR_COHORT_FUNDING_SELECTED`: it must not evaluate a funding edge), and the report lists the data limits (no spot order book so the spot leg is never borrowed from the perp book; the trade tape is only the last rows per cycle so busy symbols often have TAPE_GAP and no maker fills; queue position is estimated from visible size). Fills stay MODELLED. The exit order is sequenced by the engine: the perp exit first, the spot sell only once the venue book shows the perp closed.

**Identity.** Every one of the eight files carries the same `identity` block (`ms_types.RunIdentity`: `run_id`, `mode`, `candidate_id`, `spec_digest`, `data_digest`, `code_revision`, `generated_ms`), and `run_id` is derived from them, so two files with different identities do not belong together. `spec_digest` is `strategy_verdict.spec_digest` of the candidate file (the digest the competition binds a candidate to). `data_digest` is the sha256 of the verified manifest digests of the funding dataset, the mark dataset, the universe capture, the spot snapshot and the collector (`pipeline_summary.json.data_parts`; a genuinely absent part is the string `ABSENT`, an unreadable one `UNKNOWN`; injected test data is `UNKNOWN`). The same inputs and the same `--clock-ms` give byte-identical files.

**Why a run may be empty** (`pipeline_summary.json.status`: `primary`, `codes`, `reasons`; an empty result is a valid result, not a failure): `REJECTED_CANDIDATE` / `NO_ALLOCATION` (the candidate's `candidate_competition` verdict is REJECTED, UNTESTED or INSUFFICIENT_DATA, or has no row: it allocates nothing, though the scan is still run and shown; only a candidate the competition itself ranks PROMISING or higher may allocate, and today none is), `INADEQUATE_HISTORY` (the exact span `backfill_plan.required_window` needs, `history.required_days`, against `history.available_days`), `NO_OPPORTUNITY` (no scan had a positive-net eligible opportunity in this window), `RISK_REFUSAL`, `NO_FILL` (groups submitted, none filled: with no collector bars never fill), `SIMULATED_EXECUTION` (fills exist and every one is MODELLED), `INADEQUATE_SAMPLE` (independent closed round trips below `--min-holding-rows`), `UNKNOWN_OR_UNRECONCILED` (a ledger component unknown or a group UNHEDGED / UNKNOWN_OUTCOME; the net is `null`). Every artifact has an `evidence_basis` block: without a collector, execution is MODELLED against a synthetic book and never MEASURED.

**Scanner funding rules.** Each trailing funding print is normalised with ITS OWN interval (`MarketSnapshot.trailing_funding_intervals_min`, same length as the prints); empty or mismatched intervals exclude the symbol (`FUNDING_INTERVAL_PER_PRINT_UNKNOWN`), the current interval is never applied to older prints (a 480 to 240 change would overstate them up to 2x). The default `persistence` is a MODELLED 0.5 decay of the funding received over the hold (recorded in every row's reasons; values above 1 are refused), and a stronger provenance always ranks above a weaker one regardless of rank score.

**What the run does, in order.** Load history (`candidate_readiness.load_history_root`, verified datasets only, or injected series labelled `INJECTED_TEST_DATA`) -> scan (`ms_scanner.scan` with the instruments viewed AT the decision time: a contract delivered by then is `Closed`, one not yet launched is `PreLaunch`) -> allocate (`ms_portfolio.allocate` with `ms_risk.risk_assess`) -> the authority registers the plan BEFORE it is submitted and authorises EVERY leg body that would be sent (entry, resend, exit) -> lifecycle -> simulated fills -> `ms_accounting.Ledger` through `LedgerAdapter` -> artifacts. A refusal by the authority returns REJECTED to the engine: the order never reaches the venue.

**Reading the artifacts** (`replay_report.json`, `portfolio_state.json`, `risk_state.json`, `ledger_pnl.json`, `competition.json`, `opportunities.json`, plus `pipeline_summary.json` (the control centre DOES read it: the Research view's outcome code, required span and next step come from it; it also holds the full replay report, the policy, the authority statistics and the assumed inputs) and `reconcile_report.json`.
- Every file has `data_label`: `INJECTED_TEST_DATA` (a test's series; never `MEASURED`) or `VERIFIED_HISTORY_ROOT` (the loader verified the datasets; instrument filters are still defaulted because the capture carries none, and `pipeline_summary.json.assumed_inputs` says so).
- Bases: replay, portfolio, risk and ledger are `SIMULATED` (never realised cash); `opportunities.json` is `ESTIMATED` unless every item is derived from measured or stated inputs (then `CALCULATED`); `competition.json` is `SIMULATED` when its numbers come from replay round trips, else `ESTIMATED`. An item's provenance is the weakest of its inputs.
- `null` means unknown, never zero. `net_pnl_usd` / `realised_net_usd` are `null` when any ledger component is unknown (for example a held position's funding settled at a time with no known mark); the risk file then carries a `LEDGER_INCOMPLETE` alert. A symbol with groups but no fill is a stated zero.
- `competition.json` never says `SUFFICIENT_EVIDENCE` (modelled fills are not execution evidence). `REJECTED` with reason `NO_EDGE_IN_WINDOW` means no scan in the window had an eligible opportunity with positive net after costs: it describes that window only.
- `universe_scope` is what the loader reported; the control centre still shows `SURVIVORS ONLY` unless a verified universe capture corroborates it.

**Authority refusals you may see** in `pipeline_summary.json.authority` (`order_refusal_codes`, `registration_refusal_codes`): `BODY_FIELD_NOT_PLAN:<field>` (the body differs from the registered leg: investigate the code between the plan and the wire, nothing was sent), `GROUP_NOT_REGISTERED`, `RISK:<code>` (the authority re-assessed on fresh state), `ACCOUNT_DATA_STALE` / `ACCOUNT_TS_UNKNOWN` (stale or missing account state refuses every entry), `VENUE_NOT_ALLOWED` (only the policy's registered sandbox venue is accepted; `mainnet`, `eu`, unknown and mis-cased names are not), `SPOT_SELL_NOT_PROVEN_HEDGE_KEEPING` (a spot sell is an exit only once the perp it hedges is closed: the engine therefore sends the perp exit first).

**Policy.** `run` derives a conservative `ms_risk` policy from the symbols actually in the series (an explicit allow-list, never a wildcard; the aggregate ceiling defaults to half of equity) unless one is passed. A policy that is a wildcard, has an unknown or missing key, names `mainnet`, `eu` or a mis-cased venue, or leaves out a series symbol stops the run with `PipelineRefused` before anything runs. The policy's venue names a registered sandbox classification; nothing connects to it.

**Faults** (`ReplayConfig.faults`): lost ack, duplicate fill, restart with open orders, stale account, stale book, risk breach, instrument halt, unknown positions each leave the journal, the ledger (fees, funding, open quantities against the venue's own position read) and the artifacts consistent; an `UNHEDGED` or `UNKNOWN_OUTCOME` group is counted in `risk_state.json` and in the control centre's attention list, and no ledger figure is claimable profit while any leg is open. After a risk breach the replay still allocates and the engine then FAILs each plan (nothing is submitted): the failed-group count rises, no exposure does.

**What this does not prove.** That any candidate has edge, or that modelled fills match a venue. The pipeline is the integration of the modules; the economics are only as good as the inputs, and there is now ONE net everywhere (artifacts, equity curve and drawdown, per-trade observations, `pipeline_summary.json`): net = gross (price leg AT MID + funding) - fees - taker slippage - adverse selection, each modelled cost once. The taker walk is already inside the fill prices (added back to reach mid, then charged once); adverse selection is a modelled post-fill markout in no fill price, so it is deducted once by the pipeline's ledger adapter (ms_accounting's own net, the `ledger` dict inside the summary, omits it and is NOT the displayed net). `ms_replay.build_report` raises `ReportIdentityError` if net != gross - fees - slippage (1e-6), so a ledger on a different definition cannot produce a report. `replay_report.json` carries `slippage_usd`/`adverse_selection_usd` beside gross and fees. The control centre shows `taker_slippage_usd` / `adverse_selection_usd` from `ledger_pnl.json` as cost components, but its replay identity check `gross - fees = net` has no slippage term, so on a run WITH fills that check can report a difference equal to the modelled costs (read the components, not the check; not yet reproduced on a run with fills). The replay report's `fills` block separates `groups_planned` = `groups_submitted` + `groups_refused_at_approval` + `groups_refused_at_submit` from `groups_refused_by_halt` (opportunities withheld BEFORE allocation while the engine is halted / the symbol halted or blocked, plus plans refused at submit by a halt): the allocator no longer plans groups an engine halt can only fail. `SimVenue` enforces reduce-only (clamped to the held quantity, cumulative across exits; refused when nothing is held) and keeps its own position/balance book (spot sells cannot go short); CLOSED needs a COMPLETE venue read to show every leg key (spot included) flat. Exit quantity the authority reserved is released when an exit is rejected / cancelled / expires unfilled. **Control-centre identities (fixed, reproduced on a filled run first).** The control centre's accounting checks now use the producer's own definition: `realised_gross_usd` is the realised PRICE result at mid alone (funding is `funding_usd`), `realised_net = realised_gross + funding - fees - taker slippage - adverse selection`, and the replay check is `gross - fees - slippage = net`. A producer that states no modelled cost is checked without one; a partially stated pair is NOT_CHECKABLE (an unknown part is never zero). The ledger's `unrealised_usd` is the LIQUIDATION value of what is open (the one net includes it) while the portfolio shows mark-to-market: they differ by exactly the stated `exit_adjustment_usd`, and the check compares ledger unrealised less that adjustment with the portfolio figure. `tests/test_ms_pipeline.py` asserts every accounting check PASSES on the filled run (adverse selection, slippage and funding all non-zero).

## Canonical state, reconciliation and the halt (offline; replay, paper and testnet-adapter inputs only; no credential, no order)

Scope: `tools/ms_reconcile.py` (`reconcile`, `HaltOnDisagreement`), `tools/ms_accounting.py` (the exact ledger) and the hard loss limits in `tools/ms_risk.py`. Nothing here reads a venue or `bot/state`: the caller injects the views.

**One truth per fact.** Positions: the venue's own read (testnet) or the SimVenue book (replay / paper); engine, portfolio, ledger and artifacts are derived views and must agree with it. Reservations: the authority's durable ledger. Order ids: `orderLinkId = group_id-leg_id`. Fills: venue executions by `execId`. Funding: `(symbol, settlement ts)`. Net P&L: `Ledger.canonical_net()` (gross at mid + funding - fees - taker slippage - adverse selection, each once; open legs at the exit side of the book less the exit fee). The full table is the docstring of `ms_reconcile.py`.

**What a halt means.** When two components disagree the report has `halt_new_exposure == True` and one finding per disagreement (`POSITION_MISMATCH`, `QTY_MISMATCH`, `MISSING_IN_VENUE`, `MISSING_IN_LEDGER`, `RESERVATION_LEAK`, `RESERVATION_RELEASED_EARLY`, `STALE_VIEW`, `INCOMPLETE_VENUE_READ`, `NET_PNL_MISMATCH`, `LEDGER_INTEGRITY`), naming the key and the views. `HaltOnDisagreement.for_engine(engine)` turns that into `ExecutionEngine.halt_new_exposure("RECONCILE_DISAGREEMENT:<codes>")`; the engine then refuses every new group (`NEW_EXPOSURE_HALTED:...`) while exits and the lifecycle continue. Nothing is overwritten: the ledger, the engine and the venue read stay exactly as they were, so the disagreement can be read.

**What to do on a halt (owner).** Read the finding. `INCOMPLETE_VENUE_READ` / `STALE_VIEW`: re-read the account (a complete read with a fresh timestamp), then `HaltOnDisagreement.clear(now_ms)`. `MISSING_IN_LEDGER` / `QTY_MISMATCH` / `POSITION_MISMATCH`: find which view is wrong (the venue read is the reference) and fix THAT component from its own source (replay the fills into a rebuilt ledger with `Ledger.from_inputs`); do not copy the venue number into the ledger by hand. `LEDGER_INTEGRITY` (`ORPHAN_FILL`, `DUPLICATE_FILL_CONFLICT`, `FUNDING_CONFLICT`): two sources gave different content for one key; the first record stays booked until a human decides. `RESERVATION_LEAK`: a group is terminal in the engine but still reserved; `release_candidates` lists them and `release_leaked` releases only a terminal group on which the engine holds no position. Resume only after a clean `reconcile`.

**The ledger's words.** `status == "RECONCILED"` is internal consistency, never a venue comparison. `venue_reconciled` becomes True only after `Ledger.reconcile_with_venue(executions, positions, wallet, fees)` finds no difference (quantities 1e-9, prices 1e-8 relative, USD 1e-6) and only until the next booking. Deposits and withdrawals (`record_account_event`) move the balance and equity (`account()`), never the net. Unknown is `None`, never zero.

**Hard loss limits.** `max_daily_loss_usd` and `max_drawdown_frac` are optional policy keys. When set, `risk_assess` needs `equity_usd`, `day_start_equity_usd` and `peak_equity_usd` in the state and rejects every entry (`DAILY_LOSS_INPUT_UNKNOWN` / `DRAWDOWN_INPUT_UNKNOWN`) when one is missing; a breach rejects entries and sets `limits["halt_new_exposure"]`. Reduce-only exits are never blocked by them. `PortfolioPolicy.max_daily_loss_usd` does the same at allocation (`BLOCK_DAILY_LOSS_HALT` / `BLOCK_DAILY_LOSS_INPUT_UNKNOWN`).

## Capital book, evidence chain and the inventory tool (owner; no order, no credential)

**What the unattended engine does with capital.** Day one it deploys 40% of the $500 ceiling (never the whole grant); the compounded size never exceeds 80% of the ceiling and never exceeds your grant. Realised results come ONLY from the venue's own USDT wallet cash read at the start of consecutive sessions with the account verified flat in between: a loss is booked in full, a gain only as far as the ledger's known components explain it, unexplained cash credits nothing, and unexplained cash with funding read raises an ALERT and stops new entries. 25% of every verified gain is withheld from the sizing basis (the reserve). Two consecutive losses halve the size; four stop entries until you acknowledge. Everything is Testnet simulation, not real performance.

```bash

python3 tools/ms_testnet_autopilot.py capital                                   # the verified-realised book (no network)
python3 tools/ms_testnet_autopilot.py capital --ack-halt                        # ONLY after you reviewed the losses that stopped entries
```

**Read-only decision (`evaluate`): no authority needed, none created.** `python3 tools/ms_testnet_autopilot.py evaluate [--symbol BTCUSDT] [--notional-usd 200] [--min-funding-bps N]` answers "should anything be traded right now, and why" from the venue's public rows, books and funding plus the signed fee-rate READ (dedicated Testnet credentials, used only for that read; without them the answer is `WAIT_FOR_DATA`). Decisions: `WAIT_FOR_DATA` (a read failed or an input is invalid), `SKIP_NO_OPPORTUNITY` (no settlement can be held across, or your own funding floor is not met), `REJECT_UNECONOMIC` (expected net edge below the hurdle on the one economic model), `INCONCLUSIVE` (an input that decides the answer is only assumed, e.g. the fee tier: it can never pass), `ELIGIBLE_FOR_OWNER_TESTNET_DECISION` (the economics clear the hurdle). **Eligible is not authority**: the output lists `authority_gaps` (capability file, grant, credentials, executor lease, risk approval, venue-flat proof) and the order-capable `loop` still refuses without every one. **Economics gate (what "worth trading" means).** `tools/ms_edge_gate.py` prices the hedged round trip on the ONE economic model (`economic_model.evaluate_chain`): expected gross funding (the venue's predicted rate x (1 - 30% haircut) x the settlements inside the hold) minus fees, spread, slippage (both books WALKED at the planned size), impact, basis stress and hedge error = expected NET edge in bps and dollars. Class `PROFIT_CANDIDATE` needs every input known and NONE assumed and net >= 2 bps (`MIN_NET_EDGE_BPS`, a constant the grant cannot lower); `REJECTED_UNECONOMIC` = known but below the hurdle; `INCONCLUSIVE` = unknown, stale, thin or only assumed (an account fee tier that could not be read is ASSUMED: nothing can pass on it). The REQUIRED funding is derived from the chain, not typed in: with taker legs at Bybit's published VIP 0 schedule (spot 0.1000%, perp 0.0550% = 31 bps of round-trip fees) the requirement is about 53 bps per settlement, so a 1 bp Testnet funding print loses about 34 bps (about -$1.29 on $375). Re-check the official schedule and read your own "My Fee Rate" (the gate reads `/v5/account/fee-rate` with the Testnet key when its permissions allow it; if they do not, the tier is assumed and every cycle is INCONCLUSIVE). The owner's `--min-funding-bps` is only an extra floor; lowering it cannot make an uneconomic trade pass. A `TESTNET_MECHANICS` session (only if the grant allows it) measures lifecycle, fees and fills on fake money, is labelled in `edge_verdict.json`, and is NEVER reported as an opportunity.
- **What is still missing before any profitability claim (nothing here establishes one):** point-in-time historical validation of an entry rule (the pre-registered `reg-2` regime evaluation needs the funding backfill; run it), a measured maker fill probability (a maker-first entry would roughly halve the fee component but is not modelled as free), multi-settlement basis behaviour (a hold across more than one settlement lowers the per-settlement requirement but adds basis risk and exceeds the one-hour session lifecycle), your actual account fee tier, out-of-sample and cost-stress results with multiple-testing control, and reconciled owner-account results. It stays `PAUSED` (no trading) while the grant, the capability file, the credentials, the Supabase lease or the first recovery check is missing.
9. **Watch and export**: `fly logs -a carry-autopilot`; `fly ssh console -a carry-autopilot -C "autopilot-ctl status"`; per-session evidence is on the volume under `/data/.ai-agent-control/ms_auto_<UTC time>/` (session record, `edge_verdict.json`, `autopilot.json`, `recovery.json` if any) and in Supabase `carry.exec_events`; copy a session out with `fly ssh sftp get -a carry-autopilot /data/.ai-agent-control/ms_auto_<UTC time>/testnet_session.json`. Fly also keeps daily volume snapshots (`fly volumes snapshots list <volume-id>`); a snapshot is NOT a verified backup until you restore one into a scratch volume.
10. **Stop trading (the machine stays up and reporting)**: `fly ssh console -a carry-autopilot -C "autopilot-ctl status"` is read-only; to stop new sessions create the STOP marker with `fly ssh console -a carry-autopilot -C "su -s /bin/sh bot -c 'touch /data/.ai-agent-control/ms_autopilot/STOP'"`; an ACTIVE session is unwound (reduce-only) and verified flat. Resume with `autopilot-ctl resume --reason "..."`.
11. **Revoke authority**: delete the grant: `fly ssh console -a carry-autopilot -C "rm /data/.ai-agent-control/ms_autopilot_grant.json"`. Within about a second an active session engages its kill switch and unwinds; the loop goes PAUSED. Stopping the whole machine is `fly machine stop <id> -a carry-autopilot` (SIGTERM: the active session is asked to unwind; Fly's kill timeout is best-effort, so prefer drain first).
12. **ALERT**: the engine STAYS ALIVE in state `ALERT` / `UNRECONCILED` and never trades again by itself. Read it (`autopilot-ctl status`, `fly logs`), reconcile by hand on the venue, then `fly ssh console -a carry-autopilot -C "autopilot-ctl clear-alert --reason 'what I examined and fixed'"`; it is refused unless the venue is proven flat. The alert is kept in `marker_log.jsonl`.
13. **Recover from an unresolved session**: after a crash or a host failure the process proves flat from the venue before anything else. Flat and no open order = recorded in `recovery.json` (reconcile the accounting) and trading may continue; anything open = `UNRECONCILED` + ALERT: close it by hand with the session tool's reconcile (`fly ssh console -a carry-autopilot` then `autopilot-ctl` is not needed for that: use `cd /app && su -s /bin/sh bot -c 'HOME=/data python3 tools/ms_testnet_session.py --state-dir /data/.ai-agent-control/ms_auto_<UTC time> reconcile --unwind --confirm-plan-digest <digest>'` and pass `--confirm-plan-digest <digest>` (there is no typed prompt on the unwind)), then `clear-alert`.
14. **Safe deployment** (after a session is flat): from `bot/`, `sh deploy/safe-deploy.sh` drains (no new sessions), insists on a fresh flat proof, deploys, then resumes. It refuses to deploy over an active or unresolved session. Planned deploys must use it; a plain `fly deploy` can kill a session mid-unwind.
15. **One executor only.** Never run a second worker, a Codespace loop, `carry-drill` or a self-hosted runner against the same Testnet account. The engine needs the global Supabase lease (a second executor stays PAUSED). The legacy order-capable path (`unattended_drill.py --conformance`) now takes that SAME lease before every armed run and places nothing without it, but only in an image deployed from this code: the carry-drill machine deployed on 2026-11-05 predates that guard (see the section "Legacy apps: carry-drill and carry-book"). `carry-book` has no guard and stays stopped. The scheduled GitHub drill workflow is off unless the owner sets a repository variable (see that section).

**One command per session (read-only).** `make testnet-ready` (knobs: `NOTIONAL=400 HOLD=0 SYMBOL=BTCUSDT`) picks the next unused `~/.ai-agent-control/ms_testnet_<N>` (from 5), runs preflight, plan and `assess` chained inside the 15-minute preflight window, prints the plan digest and the state dir, and stops. It has no order path: placing the order stays the separate command you type with the digest. A size whose cushioned spot leg would exceed the ceiling is refused at plan time (use e.g. 495).

**One writer per Testnet account (execute, reconcile, unwind).** Two layers, both fail closed:
- *Across hosts: the shared Supabase lease.* The autopilot, a manual `ms_testnet_session.py execute` (its command-line entry, `guarded_main`, holds a 120 s lease and RENEWS it every 30 s for as long as the session runs; a renewal that cannot be proven engages the session's kill switch, so the hedge unwinds reduce-only and flat is verified; before EVERY entry order the server is asked again, and a lease that merely lapsed during the typed prompt is re-taken if nobody else holds it, otherwise the entry is refused), `unattended_drill.py --conformance`, an armed `drill.py --arm`, and the legacy tools `testnet_session.py`, `testnet_conformance_run.py`, `linear_stop_venue_drill.py`, `close_testnet_experiment.py` (their `__main__` goes through `legacy_executor_guard.run_guarded_cli`: lock + lease unless the command line is `--help` / `--dry-run` / `--self-check-offline`). With no `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` / `SUPABASE_OWNER_ID`, with the lease held elsewhere or with the backend unreachable they print `REFUSED` and send nothing.
- *On one host: the local account lock* (`~/.ai-agent-control/ms_executor.lock`, a kernel `flock`, released by the kernel if the process dies: nothing stale to clear). `execute` holds it for the whole session (the autopilot calls `execute` in-process, so it is covered). A second `execute`, and a plain `reconcile` (which can cancel a live leg), are REFUSED while it is held.
- *The emergency exit is never blocked and never a second writer.* `reconcile --unwind --confirm-plan-digest <digest>` takes no lease. If the lock is free it unwinds itself. If a running session holds it, the command reads who holds it, engages THAT session's kill switch (`MS_KILL` in the holder's state dir; the holder, the only journal writer, cancels entries, unwinds reduce-only and verifies flat) and waits up to the plan's exit window plus 60 s for the lock; then it verifies the venue itself. If the holder cannot be identified or never lets go it exits non-zero, names the process to stop and sends nothing. The kill file stays engaged until YOU remove it on purpose. The confirmed unwind also lifts the halt raised by repeated exit rejections (`EXIT_ORDERS_REJECTED`) with a journalled `HALT_GROUP` (empty reason plus the rejected-exit count at that moment, so only NEW rejections count towards a new halt and the next step really sends exits). Other halts are NOT lifted: a conflicting order id, an instrument halt, and `NOT_FLAT_ON_VENUE` (the engine believes flat while the venue is not: nothing the engine could send would be an exit; inspect the venue and close by hand). The handover is only made to a holder that reads a kill switch (`execute`, which includes the autopilot's sessions); a legacy tool holding the lock gets no file and the command tells you which pid to stop. The note's directory must be an absolute session directory. A lock that cannot be used at all (a directory at its path, EACCES) is not a holder: the unwind proceeds without it with a warning, a plain reconcile is refused.
- `close_testnet_short.py --arm` and `close_testnet_experiment.py --phase recover` are protective exits (reduce-only / cancel-and-flatten) and are deliberately ungated. The legacy tools do not renew their 3600 s lease, so an armed `drill.py --hold-for-settlement` whose hold + settle wait could outlive it (its defaults: 9 h + 6.25 h) is refused up front: lower `--max-hold-hours` / `--settle-wait-hours`, or use the autopilot.
- Each session also writes `exec_measurements.json` (what the executor saw and when), `execution_quality.json` (per-leg measured execution quality: reference quote, send/ack/cancel times, venue executions, maker/taker from the venue's own flag, slippage vs mid and vs touch, fees, the unhedged window, residual and the unwind) and `funding_settlement.json` (every settlement the hedge was held through and what the venue's records say it paid or charged); the autopilot turns them into `COST` / `EXECUTION_QUALITY_*` and `FUNDING` / `FUNDING_*` evidence events. Funding is booked only when the venue's Funding row agrees with the physical expectation (a short receives positive funding) and with the wallet's USDT change; otherwise it stays UNKNOWN. The sign convention of `execFee` on a real Funding row has never been observed (see docs/MONEY_MISSION.md): the first held session across a real settlement produces the row that settles it.

**Explain a refusal before retrying (read-only).** `python3 tools/ms_testnet_session.py --state-dir <the planned dir> assess` (needs the plan and the dedicated Testnet credentials; signed GETs only; places nothing, writes nothing). It prints the plan baseline, the baseline the execute step would take from the venue, the account state under each (and with none), the plan's policy caps, and the authority's own risk verdict (reasons and limits) for each leg. Use it to find out why an order was refused (`RISK:*_ABOVE_CAP`) from numbers, and send the output (it contains no secrets) rather than re-running `execute`. First clean real Testnet cycle (run 4): the perp filled, the spot limit IOC, priced AT the plan-time ask, was cancelled because the market drifted ~15 bps up before execute, and the engine unwound the unhedged perp flat (fees $0.41). The spot buy limit is now `SPOT_BUY_CUSHION_BPS` (30) above the ask (still fills at the best ask; only the worst price is bounded) and the plan refuses a size whose cushioned spot leg would exceed the ceiling (`SPOT_LIMIT_NOTIONAL_ABOVE_CEILING`: ask for a little less, e.g. 495). Root cause of the second real refusal (`RISK:PER_SYMBOL/AGGREGATE/GROSS/UNHEDGED_*_ABOVE_CAP` on a plan that fits every cap): the engine sends both entry legs in one loop; the first leg filled at once, so the second was assessed with the first counted twice (venue position AND still-reserved leg). Entry legs the venue's own order read shows fully filled are now settled before the next leg is sent, and the account state is re-read after it. No cap, gate or guard changed. Spot balances are subtracted from the pre-session baseline in decimal, not float (a 0.1 BTC holding made an exact-lot spot sell look 1e-17 too large and the exit was refused `SPOT_SELL_NOT_PROVEN_HEDGE_KEEPING`).

**Arm it (once).** Rebuild the Codespace (or run `make setup`): installs the pinned requirements, builds the native core, creates private directories (`~/datasets`, `~/seals`, `~/backups`). Add the two Codespaces secrets `BYBIT_TESTNET_API_KEY` / `BYBIT_TESTNET_API_SECRET` ONLY when you want the Testnet preflight (a Testnet key with Contract Orders&Positions and Spot Trade, no withdrawal or transfer); preflight ALSO needs the owner capability file from "Testnet execution: owner procedure" step 4, and fails without it. `make check` runs the secret scan, the frozen-strategy proof and the Fly build-context check; `make test-quick` runs the integration suites.

**The layout the Makefile finds (one layout; override any piece on the command line).** Under `~/datasets`: `universe-v3-<UTC ts>/` (the universe capture; `UNI`, newest), `md-<UTC date>/` (history roots; `HIST`, newest, which `make plan` and `make diagnose` subtract), `full-history/data` (what `make backfill` writes; once it exists `make pipeline` and `make regime-eval` evaluate it unless you pass `HIST=`), `spot-snap/spot-instruments/snapshot-<ms>/` (`SPOT`, newest; `python3 tools/market_history.py spot-instruments --out-root ~/datasets/spot-snap`), `md-collector/` (the supervised collector root), `pipeline-out/run-<END>/` with `pipeline-out/latest` linked to the newest run (the control centre reads `latest`, and `~/.ai-agent-control/ms_testnet` for the testnet session), `ledgers/`. **The data steps (read-only / public, in this order).**
1. `make scope` and `make diagnose`: judge the universe capture from its raw bytes and explain the loader's symbol count (`why_few_symbols`). `UNI=` and `HIST=` default to the newest `universe-v3-*` / `md-2*` under `~/datasets`; override on the command line.
2. `make plan` then `make backfill`: the sealed 457-day plan and the resumable public collection into a NEW directory (`~/datasets/full-history/`); re-run `make backfill` to resume.
3. `make collect-start`: a supervised public order-book/trade collector. It records your intent in `~/.ai-agent-control/ops/ENABLED`, so after a Codespace stop/start `postStartCommand` (`make ops-resume`) restarts it; `make collect-stop` removes that intent and writes the stop file. `make collect-status` shows the supervisor, any `ALERT` and the collector's own `health.json` fields (status, last cycle, failures, refusal, `disk`, last seal / backup / restore-check); `make collect-log` tails the supervisor log.
4. `make seal`, `make backup`, `make restore-check`, `make audit` (the collector also runs these hooks itself on its cadence). `"ok": true` from `restore-check` is the only proof a backup restores; `make audit` states freshness and research readiness on separate axes.
5. `make control-centre-start` serves the read-only control centre on `127.0.0.1:8787` (private forwarded port); `make pipeline START=<ms> END=<ms> SPOT=<spot-snapshot-dir>` is a REPLAY research run (TESTNET and live modes are refused by the CLI) whose artifacts the control centre displays.
6. `make testnet-preflight`, `make testnet-plan`, `make testnet-status`: GET-only preflight and the offline plan. Read the printed plan digest; the one command that can place a Testnet order stays in "Testnet execution: owner procedure" and is typed by you.

**What the supervisor does and does not do.** It restarts the collector after an unexpected exit with back-off (15 s doubling to 10 min) and starts a new 24 h segment after a clean one. It STOPS, writes `~/.ai-agent-control/ops/ALERT` and does not retry when the collector's `health.json` says `REFUSED` (free space under the reserve, the cycle log needs `repair-log`, a non-private root), after six consecutive failed segments, or when the stop file exists. `ALERT` present means a human decision is needed: read `health.json`, fix the cause, `rm ~/.ai-agent-control/ops/ALERT`, `make collect-start`.

**What a Codespace cannot do.** A Codespace stops after its idle timeout (raise it in GitHub settings, at most 4 h of true idleness) and a stopped Codespace collects nothing: the downtime is recorded as a gap, never filled. It resumes when you open it (or any connected client keeps it alive). A collector that must not have gaps needs a host that does not sleep; where that runs is your decision and a Fly change is yours to make (`bot/DEPLOYMENT.md`), not part of this layer. Keep the disk reserve: the Codespace volume is finite; `make collect-status` shows `disk`.

**Known limits.** `.devcontainer/devcontainer.json` grants the Codespace token write access to contents, pull requests, workflows and actions for this repository; that is broader than a paper/testnet-only session needs and is the owner's decision (it was not changed here). The candidate spec `funding_regime_conditioned_entry@spec-1` (BTC only, exit on regime OFF, thresholds fitted on 70% of the BTC corpus) and the evaluator registration `@reg-1` (all hedgeable symbols, fixed 30-day hold, thresholds from cost arithmetic) are different documents; the evaluator's registration is the one that is run.

**What this does not do.** It does not place orders, does not enable Mainnet, does not sign the promotion gate, and does not turn research into profit: a strategy is traded only after it survives verified history, the competition gate and a confirmed Testnet session, and the current answer from the committed BTC corpus is NO WINNER (cash_and_carry INSUFFICIENT_DATA). The route to money is: full-universe history (steps 1-2) -> the competition on it -> a promoted candidate -> the Testnet lifecycle -> your own gate decision.

## Regime-conditioned carry evaluator (pre-registered; offline, read-only, one trial)
`tools/regime_entry_eval.py` tests ONE frozen hypothesis, `funding_regime_conditioned_entry@reg-1`: enter a hedged spot+perp pair only while the funding regime is rich and persistent, hold 30 days, exit at the end. The regime state at decision time uses only prints at or before that time, each normalised by the interval of its own segment: trailing 7-day mean funding >= 2.0 bps/day AND >= 80% of those prints positive AND >= 3 prints. The level is arithmetic on costs (the 31.4 bps spot+perp taker round trip over 30 days is 1.05 bps/day; the registration asks for about twice that), not a fitted value. `--print-registration` (no other argument needed) prints the frozen registration and its digest; the digest is recorded with every result, and changing a number is a different registration (a new id, a new trial).
- **Run it** (after the history root is collected): `make regime-eval HIST=<data root> UNI=<universe dir>` (SPOT defaults to the newest snapshot under `~/datasets/spot-snap/spot-instruments`; without one the target stops and says so instead of passing an empty `--spot-dir`; `HIST` defaults to `~/datasets/full-history/data` when it exists, else the newest `md-2*`) or `python3 tools/regime_entry_eval.py --history-root R --universe-dir U --spot-dir S --mark-interval 240 --ledger-dir L --json OUT`. The full report goes to `OUT`.
- **One trial.** The persistent ledger `<ledger-dir>/funding_regime_conditioned_entry.jsonl` counts the variant once; an identical re-run is the same trial and never enlarges the family. Do not tune the thresholds and re-run: that is a search and must be a new registration, counted.
- **What it can say.** The verdict is capped at INSUFFICIENT_DATA. A 30-day hold gives about 15 non-overlapping rows on a 457-day capture, far below the 50 the repository requires, so today it reports `TOO_FEW_HOLDING_ROWS` with a DESCRIPTIVE in-sample result (row mean/median/worst, share of rows positive, coverage, concentration in the top symbols, by funding interval, regime persistence). That tells you whether prospective evidence is worth collecting, not whether to trade. The capture window was already seen by other families, so even a good descriptive number is NOT a clean hold-out.
- **Basis residual.** With a verified `index-kline-<interval>` dataset (collect it with `market_history.py run-plan --datasets index-kline` against the plan) the residual `-(mark return) + (index return)` is measured per leg and reported separately; it never enters the registered metric. The index is Bybit's multi-exchange index, a PROXY for the Bybit spot pair, so the residual includes the index-vs-spot tracking error. Without the dataset it is UNMEASURED.

**reg-2 (post-hoc, second trial).** `--registration reg-2` / `make regime-eval REG=reg-2 HIST=... UNI=...` runs the same entry plus ONE added exit: at daily checkpoints, exit when the trailing 3-day mean funding (interval-normalised, prints with key <= the checkpoint only) is below 0; otherwise the end of the hold or deliveryTime; one round trip per position, no re-entry in the hold. It was written AFTER reg-1's result (14 rows, mean -78.6 bps, median leg +32.6 bps, a heavy negative-funding tail, the entry condition already false at a later weekly checkpoint for 55% of legs); reg-1 registered a fixed hold although the draft spec's exit list named funding inversion. It is the SECOND trial in the family ledger (`n_variants_counted` becomes 2 and its adjusted p-value counts both), it is flagged `post_hoc: true` in every report, and the early unwind is charged the same taker round trip (no extra slippage is modelled). Run each registration once; reg-1's digest (`5cc46d3febdde88b...`) is pinned by a test and must never change.
